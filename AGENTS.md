## Build & test

The core library is two CMake projects: the root (library + CLI + unit tests) and `benchmarks/` (standalone, FetchContent-pulls external solvers).

```bash
# Root project
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)

# All tests (gtest_discover_tests registers each TYPED_TEST instance)
ctest --test-dir build --output-on-failure

# Single test or filter
./build/tests/unit_tests --gtest_filter='FactorizeTest/*.PermutationIsValid'

# CLI solver (a RHS is mandatory: --rhs file.mtx or --random-rhs). The input
# .mtx may be an assembled Laplacian/SDDM operator or a graph adjacency/pattern
# matrix; the kind is auto-detected and reported (`--input-kind` overrides).
./build/apxchol path/to/matrix.mtx --random-rhs --tol 1e-8
```

The direct forced-GPU campaign checked 90/90 T=16 records over ten matrices and produced a 1.102x setup geomean versus the bracketed CPU path. A separate exact asynchronous persistent kernel, shaped after ECL-MIS but independently implemented with the repository's full priority order, preserved factors and iterations in 54/54 bracketed runs; it still made selector time 1.057x and `find_partition` 1.069x overall (including 1.580x selector time on com-Amazon), while setup was noise-level 0.989x. It therefore did not rescue the mode. The GPU block-region frontend below is independent and remains.
  - **GPU block front-end transfer path (2026-08-23):** active vertex ids, active degrees, candidate filtering and the selected-degree work sum remain device-resident across rounds; production does not upload the active list or download all active degrees. Parallel elimination exposes non-owning views of its existing `deferred_edge {u,v,w}` buffers. A bounded 1M-edge (16 MiB maximum) staging buffer copies those records contiguously and a GPU kernel extracts `{u,v}`, avoiding both an endpoint-only CPU write and a second host copy. The retained benchmark history records a 0.973x setup geomean against the previous transfer path over grid_500, iter0040, com-Amazon, as-Skitter and coPapersDBLP; a strided `cudaMemcpy2D` gather was rejected after making `advance` 8-27x slower. This machinery is now owned solely by the block-region frontend.
  - **GPU block/region setup front-end (2026-08-23; `gpu_block_frontend.h` / `cuda_block_frontend.cu`):** for `bg+tree` on either pooled adjacency representation (`vec_pool` or `vec_pool_aos`), `APXCHOL_GPU_BLOCK_FRONTEND` is **AUTO when unset**: use the GPU at **at most 8 host OpenMP threads**, otherwise stay on the CPU. Supporting both layouts is semantic, not just performance: changing graph storage must not silently change the selector, and `VecPoolAos.SerialFactorMatchesIndexedVecPoolByteForByte` guards the resulting factor equality. `=0|off` is the rollback; `=1|on|force` bypasses the thread governor and fails loudly if cooperative launch or memory fitting is unavailable; `=auto` names the default. The boundary follows the measured CPU-selector scaling crossover, not graph size: a strict GH200 single-RHS campaign checked 270/270 records over nine matrices, bracketed CPU/GPU/CPU; total-time geomeans were **0.711× / 0.762× / 0.826× / 0.927× at T=1/2/4/8**, then **1.050× at T=16** (three per-seed geomeans 1.034/1.055/1.062) and **1.201× at T=72**. Peak host RSS is about **1.21×** overall; the GPU path still loses on com-Amazon (1.21× total at T=8) and grid_2000 (1.41×), so this is a throughput default, not a per-matrix dominance claim. The selector reuses the device-resident residual topology while preserving the independent-region model: one warp serial-greedy-scans each contiguous candidate region, a snapshot pass removes cross-region conflicts under `(degree,index)`, and a cooperative frontier-restricted repair restores maximality. Region count defaults to the number of region-scan warps that can be resident on the GPU (`3648` on the RTX 4090 Laptop); `APXCHOL_GPU_BLOCKS=<positive>` is A/B-only. `APXCHOL_GPU_BLOCK_TRACE=1` prints per-round timings. `GpuBlockFrontend.*` compares the result with an independent CPU specification and checks determinism, independence and maximality. Exact-clique mode, unsupported cooperative launch and insufficient free VRAM fall back under AUTO and remain errors under `force`. The earlier `n >= 500000` governor was rejected: initial size does not predict the result (grid_2000 loses while smaller iter0040 wins).
  - **Dataflow backend (the DEFAULT GPU SpTRSV — AUTO — since 2026-08-18, and since 2026-08-20 the only one the library implements; `APXCHOL_GPU_SPTRSV=dataflow` names it explicitly, `=cusparse` overrides; `include/apxchol/solver/sptrsv/cuda_dataflow.h`, the file header is the design note):** a sync-free triangular solve with O(n) STATE — ONE persistent kernel launch per sweep (vs one launch per level on the removed level-set backend, 70–100 per sweep, and cuSPARSE's O(nnz) analysis buffers), on CSR of L / CSR of L^T, no level schedules at all. Every row owns an 8-byte epoch-tagged word `{value, epoch}`; warps claim batches of consecutive rows in natural (forward) / reverse (back) row order — a topological order of the factor, coalesced, and for an elimination factor roughly level order — with one atomic ticket; the host packs rows into 32-lane batches with lane groups G = 1, 2, …, 32 by row length (`cuda_host::dataflow_batches`, `dataflow_lane_group`, per-lane prefetch depth `dataflow_prefetch_depth()` = 8), so every row's structure is prefetched into registers before the wait; lanes poll the tagged words of their missing neighbours (pending-mask, only laggards re-read; clock spin 100→800 ns between polls — `__nanosleep`'s granularity is ~1 µs on this GPU), a row publishes value + flag in one 64-bit store: no fence, counter or atomic on the data path. Deadlock-free by construction (a lane only waits on smaller tickets, all held by running warps; the grid is the exact resident block count, `dataflow_grid_size()`, env `APXCHOL_GPU_DATAFLOW_BLOCKS=<n>` overrides for A/B). Bit-deterministic run to run and across grid sizes (cuSPARSE is not). fp32 values (the tagged word packs a 4-byte value next to a 4-byte epoch), fp16 storage supported. **ROW SEGMENTATION (2026-08-20, the fix for the hub-factor gap):** a row is walked by its lane group in chunks of `G*kPre` entries with G capped at 32, so an unsplit row is `ceil(len / 256)` load→poll→accumulate round trips deep ON THE CRITICAL PATH — chunk k+1's loads cannot issue before chunk k has been polled to completion — and a hub factor's elimination tail is a CHAIN of such rows (`APXCHOL_GPU_SPTRSV_STATS=1`: com-Orkut's forward CSR holds **84% of its 544M-nnz factor in the 10% of rows at least 256 entries long**, longest 134368; com-LiveJournal 63% of 122M, kron_g500-logn16 90% of 4.0M; com-Amazon only 11% of 2.0M, iter0040 0.01%, grid_500 none). The host therefore CUTS such a row into S **segments** of one chunk each plus one **finalizer** (`cuda_host::dataflow_build_plan`): a segment is a full 32-lane item over one CSR slice that accumulates exactly as an unsplit G=32 row would and publishes its partial into an extra epoch-tagged SLOT word `tag[m + slot]` — the partials live in the SAME array as the rows, so a stale slot is rejected by its epoch and no per-sweep memset is needed; the finalizer polls the S slots IN FIXED INDEX ORDER (no CSR, no value loads, no atomicAdd anywhere), divides by the diagonal and publishes the row. The S+1 items are ALONE in their batches (the segments' zero-width in sweep positions, the finalizer's owning the split row's), so `batch_start` stays monotone, the common path is byte-for-byte unchanged behind ONE broadcast `batch_spec[b]` load per BATCH, ticket order stays sweep order with a row's segments before its finalizer (every wait is still on a strictly smaller ticket — the deadlock argument carries over verbatim), and the kernel's IMPLICIT "a multi-chunk item never shares a warp with a possible producer" property survives (asserted host-side in `cuda_host::dataflow_plan_check`, which setup runs on both plans and throws on). Determinism is untouched: the split is a pure function of row lengths, so the output is still bit-identical run to run AND across grid sizes (it does differ from the unsplit kernel's, by association — a forced S=1 split is bit-identical, which is the protocol-isolation test). Device state grows by `4 B/batch` + `16 B/spec item` + `8 B/slot`: com-Orkut, the biggest, pays 59 MB of tables and 1.95M slots against a 544M-nnz factor. **THE THRESHOLD IS DERIVED, NOT A CONSTANT** (`cuda_host::dataflow_split_threshold`, per direction, from that direction's histogram): where rows ≥ one chunk hold ≥ 25% of the nnz the aggressive threshold C = 256 wins, elsewhere only rows past the depth break-even 3C = 768 are cut — the same threshold that is **2× on kron_g500 is +31% on com-Amazon**, whose long rows are 11% of the work and whose extra batches are pure overhead. Measured (RTX 4090 Laptop, T=16, bg+tree[vec_pool], default drop + fp16 storage, `gpu_pcg_loop` **ms per PCG iteration**, interleaved medians, against the PRE-CHANGE binary in the same session): **kron_g500-logn16 17.28 → 8.97 (0.52×; total solve 251 → 129 ms), com-LiveJournal 153.1 → 50.6 (0.33×), com-Orkut 726 → 136 (0.19×)**; neutral where nothing splits — iter0040 0.947 → 0.925, grid_500 0.393 → 0.394, com-Amazon 2.114 → 2.117 (the null control, pre-change vs new-with-segmentation-off, spans 0.95–1.02× on those three, i.e. the differences are noise).   - **No closed-source dependencies (2026-08-18; branch `gpu/no-closed-deps`):** the CUDA library links **`CUDA::cudart` only**. The GPU-resident PCG (`pcg_cuda.h`) runs OUR OWN kernels (`include/apxchol/solver/pcg_cuda_kernels.h`, `src/cuda_pcg_kernels.cu`, namespace `apxchol::pcg_cuda`) instead of cuSPARSE SpMV + cuBLAS dot/nrm2/axpy/scal: a CSR SpMV with p·Ap folded into the row loop (`spmv_pAp`; LANES ∈ {1,…,32} consecutive threads per row — the CUSP vector-CSR family, `spmv_lanes_for(avg nnz/row)` = the power of two nearest to the average in log2, so grids (~5/row) get 4 and the IPM factors (~15/row) 16; env `APXCHOL_GPU_SPMV_LANES=1|2|4|8|16|32` overrides for A/B, `cuda_pcg::spmv_lanes()` reports; fp64 operator values or the fp32-exact operator's fp32 values promoted per product, fp64 accumulate — the fp32-exact rule mirrors the CPU's `op_fp32_`, `APXCHOL_GPU_FP32_OPERATOR` overrides as before), the fused vector passes of the CPU loop (`update_xr` = x += αp, r −= αAp, r·r in one pass; `dot` for r·z; `update_p` = z + βp) and DETERMINISTIC reductions: a fixed grid (`pcg_blocks(units)` = min(ceil(units/256), 2048), a pure function of n), each thread a fixed strided subset in a fixed order, a fixed-order warp-shuffle + shared-memory tree per block, one partial per block, a fixed-order single-block final reduce (`reduce_partials`) → 8 bytes back into pinned host memory — no floating-point atomics anywhere, three host syncs per iteration (p·Ap, r·r, r·z), so together with the dataflow / level-set SpTRSV the whole GPU solve is bit-identical run to run (`SolveTest.DeterministicWithSameSeed` on the CUDA build, `--gtest_repeat=25` clean). It is constant in n, in T and in the factor size: **~80–135 ms on the RTX 4090 Laptop, ~715 ms on a GH200** (Grace: 55% of the whole reported setup; `/home/adamant/.cache/apxchol_prof/daint_gpu_setup_breakdown.md`). GPU persistence mode is NOT a substitute (laptop 80–97 → 76–86 ms measured). Two independent changes:
    1. **Library.** `apx_cholesky::factorize` calls `cuda_ctx::prewarm()`, which starts ONE helper thread per process (mutex-guarded, started at most once, joined by `ensure_context()` or by the state's destructor — so a process that never touches the GPU still exits cleanly) doing `cudaFree(0)`, so the context is created WHILE make_graph / find_partition / eliminate / assembly run. `apx_cholesky::install_factor` then calls `cuda_ctx::ensure_context()` immediately BEFORE `trsv_.setup` and records the REMAINING wait under its own checkpoint label **`cuda_init`** (plus a `[sptrsv-setup gpu] cuda_init … (context creation … ms)` line under `APXCHOL_SPTRSV_SETUP_TRACE`). Correctness never depends on the prewarm: the primary context is reference-counted and its creation is serialized inside the driver, so the helper racing the main thread is well defined — the prewarm only decides WHEN the cost is paid, `ensure_context()` alone makes it VISIBLE and keeps it out of `sptrsv_setup`. Without `APXCHOL_USE_CUDA` the whole header is empty inline functions, so call sites carry no `#if`.
    2. **Benchmark driver.** `benchmarks/src/benchmark.cpp` does one `cudaFree(0)` before ANY solver is timed and prints `[bench] cuda_init (once, before any timed solver): … ms`. This is a **fairness** measure, not an optimization: every GPU competitor (`amgcl_cuda`, `hypre_boomeramg_gpu`, the GPU RCHOL / ParAC drivers) paid the same lazy cost inside its own measured setup, and hiding only ours would tilt the tables.
    **Consequence: published GPU setup numbers change meaning.** Every historical GPU setup cell is inflated by one context creation — including `--repeat 2` ones, because `median_run` with 2 repeats returns the SLOWER of the two runs, which is the cold one 80% of the time (measured, 30 pairs). **The benchmark cells need regenerating.** Measured on the laptop (RTX 4090 Laptop, T=16, `bg+tree[vec_pool]`, 5-arm interleaved A/B with an A-vs-A null control, 12 reps/arm/cell; context creation there is 78–353 ms, median 87): the cold-minus-warm gap of the FIRST setup in a process collapses — `sptrsv_setup` **grid_500 +90 → +3 ms, grid_2000 +94 → +16 ms, iter0040 +99 → +12 ms**, and with the harness warmup as well **grid_500 setup 207 → 69 ms (−67%)**, grid_2000 1310 → 1138, iter0040 844 → 777. Warm setups are unchanged; iterations and residual are bit-identical (T=1: grid_2000 50 / 8.383146e-09, iter0040 46 / 7.393451e-09 on both). Caveat, and it is in the header: the overlap is worth at most min(host setup, context) because context creation is CPU work — on grid_500, whose host setup is shorter than the context, the library prewarm alone is a wash (154 → 156 ms) and only the harness warmup helps. **Refuted in the same pass:** parallelizing `cuda_host::csr_row_lengths`, the only part of `setup_kernel_backend` that is not `dataflow_batches`, costs `kernel_backend_tables` **12.3 → 20.3 ms** on grid_2000 (its consumer reads `len` back serially); see the comment on that function. `dataflow_batches` is ~85% of the stage and is the only lever left there.
- `-DAPXCHOL_64BIT_EDGE_INDICES=ON` — 64-bit `edge_index` (cumulative offsets/edge ids) for factors or residual pools exceeding the default unsigned-32-bit capacity (2³²−1 entries). com-Orkut's roughly 2.15B-entry raw factor fits the default build; this was the purpose of moving offsets from signed to unsigned 32-bit. `-DAPXCHOL_64BIT_NODE_INDICES=ON` additionally widens vertex ids (implies 64-bit edges). The old `APXCHOL_64BIT_INDICES` is a deprecated alias for the EDGE knob. The standalone `benchmarks/` project exposes the same two options. See `include/apxchol/types.h`.
- `APXCHOL_POOL_FP32` — **ON by default** (fp32 residual-pool edge weights); pass `=OFF` for an fp64 baseline. The SpTRSV's own factor values are fp32 **unconditionally** — the `APXCHOL_SPTRSV_FP32` option was removed 2026-08-20 together with the fp64 storage path it gated (`factor_value_t` = `sptrsv_value_t` = `float` in `sparse_csc.h`, `cuda_value_t` = `float` on the GPU). Nothing shipped or was measured against the fp64 storage, and the GPU's dataflow backend never supported it (its tagged word packs a 4-byte value next to a 4-byte epoch), so the only thing the option bought was a second, untested compile of every SpTRSV path.
- **fp16 SpTRSV factor storage is a RUNTIME switch, not a build option** — `APXCHOL_SPTRSV_FP16=0|1`, read by BOTH backends at every setup (`apxchol::sptrsv_fp16_env_tristate()` in `include/apxchol/lowprec.h` is the one reader; `omp_sptrsv::fp16_from_env()` / `cuda_sptrsv::fp16_resolved()` apply the per-device default). **Unset resolves per device: ON on the GPU, OFF on the CPU** — the two have opposite measured verdicts (GPU: −12% `gpu_pcg_loop` on iter0040, −4..8% grids, −15..20% device factor bytes, iteration-neutral on all 9 suite matrices; CPU: a memory lever whose iteration cost has to be paid back, so opt-in). The CPU kernel is INSTANTIATED for both storage types (`omp_sptrsv::setup_impl<V>` / `solve_levelset<Dir, V>`, V = `float` | `fp16_t`) and `setup` branches ONCE on the env — never per row — so one binary does either. `APXCHOL_GPU_SPTRSV_FP16` (the GPU-only name until 2026-08-20) is still read as a DEPRECATED alias with a one-shot stderr note; since it aliases the unified variable it now governs the CPU too. **Distribution guard:** the fp16 storage is only compiled and only offered where the target has F16C (`omp_sptrsv::fp16_supported()`, `__F16C__`); without it the fp16→fp32 widen becomes a libgcc `__extendhfdf2` call in the inner loop (measured 3× slower solve), so a portable baseline-x86-64 build — the PyPI wheels — compiles fp32 ONLY and the env falls back with a note. The storage itself is unchanged: IEEE binary16 of `L_ij / s_j`, per-column `s_j` = max |off-diagonal| (`omp_sptrsv::column_scale`), fp32 diagonal in a separate `diag_[]` (`omp_sptrsv::stored_diag` + the column's rounding residual), fp16 subnormals flushed to signed zero, the scale FOLDED INTO THE VECTORS (`forward_solve` returns `y' = D y`, `transpose_solve` takes `y'` and scales its input by `inv_scale_[j]^2` — `preconditioner.h` only ever calls the pair), fat-level (`omp for`) kernels SIMD on AVX2+F16C+FMA (`omp_sptrsv::simd_fp16_kernel()`: 8 values per `_mm256_cvtph_ps`, stack buffer, 4-way scalar FMA chain), arithmetic always fp64. **Degenerate scales** (both backends, same contract): a column whose fp32 `1/s_j` or `fp32(L_jj)/s_j` would overflow falls back to `s_j = 1` before the drop (`lowprec_stats().scale_fallback`); setup then verifies every diagonal is finite and nonzero and every `r_j^2` finite, and THROWS otherwise — a factor the storage cannot represent fails loudly instead of dissolving into NaN. Any new consumer of stored factor values must `widen()` them (`fp16_t`'s float/double conversions are explicit on purpose). **Removed 2026-08-18:** the `BF16` / `BF16_SCALED` (bfloat16, 7-bit mantissa; RNE or stochastic rounding) and `FP24` storage variants and their types/tests — bf16 cost 3–6× the PCG iterations on IPM, fp24 was marginal. **Removed 2026-08-20:** the `APXCHOL_SPTRSV_LOWPREC` CMake cache variable itself (root + `benchmarks/`), which had made the CPU storage a compile-time choice and forced CUDA builds to treat it as OFF.
- Runtime env knobs of the OpenMP SpTRSV / CPU PCG (both storages; read per setup). After the 2026-08-20 surface reduction this list is ONE entry — everything else that used to sit here is in "Retired knobs" below:
  - `APXCHOL_FACTOR_DROP=<rel>` — the COMPACTING drop with column-sum compensation (the compensation is unconditional; the threshold is the only knob), **ON by default at 1e-4**: see "Compacting factor drop" below (that section is authoritative). What the storage format adds to it: the pure predicate `omp_sptrsv::keep_offdiag(v, s_j, rel, fp16_flush_subnormal)` also drops what the storage format would store as zero anyway (`omp_sptrsv::format_flushes`: exact zeros on fp32/fp64; on FP16_SCALED also everything fp16 flushes, subnormals included by default — at the default rel = 1e-4 > 2^-14 this adds nothing), the drop and the compensation run on the fp32 factor BEFORE `narrow_value` (dropped entries never reach the storage format; `s_j` is the pre-drop column max), and `omp_sptrsv::lowprec_stats()` (== `drop_stats()`, one record) splits `dropped` into `dropped_threshold` + `dropped_flush` next to `rel` / `compensate` / `nnz_factor` / `nnz_stored`. Supersedes the removed `APXCHOL_LOWPREC_DROP` diagnostic (same threshold and numerics — a stored zero and an absent entry solve identically — but that one only zeroed in place).
- `APXCHOL_BUILD_EXAMPLES` / `APXCHOL_BUILD_TESTS` — both ON by default; `APXCHOL_BUILD_TESTS` gates the GoogleTest fetch. `APXCHOL_BUILD_TOOLS` — OFF by default; builds the `bench_setup` / `analyze_factor` dev tools. `analyze_factor MATRIX --solve [--seed N]` is the lightweight single-RHS diagnostic: CUDA builds prewarm the process context before the timed setup, then print one parseable `solve_result` line with setup, PCG, total, iterations, residual and solver VRAM. Adjacency inputs are exact graph Laplacians, so the diagnostic projects its random RHS separately in every connected component; a merely global projection is incompatible on disconnected graphs such as as-Skitter.

The project targets **C++23** (`CMAKE_CXX_STANDARD 23`) and adds `-march=native` in Release/RelWithDebInfo.

## Architecture

### Library layout

The public surface is the header tree under `include/apxchol/` plus two compiled TUs (`src/factorization.cpp`, `src/solve.cpp`) that form `apxchol_core`. The convenience header is `include/apxchol.h`. Subdirectories:

- `apxchol/graph/` — graph data structure templated on an `incidence_storage` concept. Implementations: `vec` (std::vector), `forward_star` (linked-list pool), `bstr` (bit-string), indexed `vec_pool`, and the high-level/default `vec_pool_aos` (the same slab allocator with inline directed `{neighbor, weight}` records and no shared edge pool). Active-vertex state is shared by every layout and packed at one bit per vertex; relaxed atomic word clears preserve concurrent bulk deactivation when selected vertices share a word, while round barriers order later readers. This replaces the byte-per-vertex array without changing factors: the strict Grace gate checked 72/72 exact records over nine matrices at T=16/72; `find_partition` / setup / one-solve-total geomeans were 0.977/0.993/0.993, led by Orkut setup at 0.946/0.978. The gain is a cache/memory constant, not a scaling claim: setup was 0.990 at T=16 and 0.996 at T=72. Pooled-slab filtering finds the first dead entry before writing a stable compacted suffix, so an already-clean slab is a read-only pass instead of copying every survivor onto itself. The strict GH200 gate checked 72/72 exact records over nine matrices at T=16/72: prune / setup / setup-plus-one-iteration geomeans were 0.869/0.979/0.980, with setup 0.978 at T=16 and 0.981 at T=72. This is likewise a memory-traffic constant, not a scaling win (relative T16-to-T72 setup scaling 0.997). With 32-bit nodes and fp32 weights both pooled layouts carry 16 B of logical residual payload per undirected edge: indexed = one 8 B edge plus two 4 B indices; AoS = two 8 B records. Both keep unused geometric pool capacity lazily paged (`big_alloc<..., Populate=false>`): live `resize()` slots are still initialized, and THP advice remains, but `MADV_POPULATE_WRITE` does not commit capacity that has only been reserved. The strict GH200 gate checked 462/462 eager/lazy/eager records (11 matrices, T=1/16/72, indexed + AoS): lazy paging kept factor structure and iterations identical within every triplet, reduced peak RSS to 0.899x overall (indexed 0.944x, AoS 0.857x), and was mildly setup/total positive at 0.983x/0.991x. On the resulting lazy allocators, the 77 direct AoS/indexed cells are 0.807x setup and 0.868x single-RHS total at 1.102x RSS (total 0.815x/0.867x/0.887x at T=1/16/72), which is why the high-level API, CLI and benchmark headline use AoS. Parallel AoS apply reuses the endpoint histogram's atomic return values as final slab offsets, writes each incidence directly, and publishes each touched slab once; this removes the apply pass's second pair of endpoint atomics without duplicating weights. Its temporary cost is two 32-bit offsets per emitted undirected edge. Current-main GH200 job **4538334** checked 162/162 full solves, 54/54 exact brackets and a 20-repeat byte-equality guard over nine matrices, three seeds and T=16/72: setup / elimination / one-RHS-total geomeans were **0.955/0.894/0.971** and **0.936/0.896/0.954**; factor nnz, stored nnz and iterations were unchanged in every cell, every matrix total stayed below 1.03x, and aggregate peak RSS was 0.984x / 1.025x (Orkut 1.021x / 1.016x). The measured path is unconditional for parallel AoS; there is no runtime knob or second production implementation. The only structural difference was the indexed-only multiplicity-preserving late residual coalescer, firing in 3/77 as-Skitter groups. A 45/45 GH200 follow-up tested an AoS-main/indexed-coalesced-tail bridge: it reproduced indexed factor/iterations/residual exactly, but versus plain AoS raised total time to 1.038x/1.068x/1.059x at T=1/16/72 and cost one PCG iteration at T=1 and T=72; com-Amazon and grid controls were exact no-ops. **Rejected:** do not add a multiplicity field or hybrid handoff to AoS. Plain AoS's three differing factors had the same iterations once and one fewer twice, so byte identity with indexed is not a quality requirement. Keep indexed coalescing itself: an 18/18 on/off isolation on those trigger groups had setup/PCG/total geomeans 0.970x/1.033x/0.994x (total 1.010x/0.981x/0.989x at T=1/16/72). `graph_storage` in `types.h` selects the backend via `make_graph<...>`; explicit indexed `vec_pool` remains available for its lower peak-RSS profile.
- `apxchol/solver/` — factorization and PCG glue.
  - `elimination/` — the tree-based clique-sampling kernel plus the public `eliminator` seam (`weighted_neighbor`, `deferred_edge`, `edge_emitter`, `random_stream`, `as_eliminator`; per-elimination seeds — no library-owned RNG stream); its canonical neighbor order uses exact stable weight-radix plus vertex tie sorting from degree 2048, and the sampler uses an exact coarse inverse-CDF directory from degree 512; the `clique`/`iid` variants no longer exist.
  - `partition/` — independent-set partitioners (`block_greedy` default, plus `priority_greedy` and `baumann_kyng`); the list lives in `partitioner_list.h`. The old `luby` name was inaccurate (its priorities were fixed within a round), and the Blelloch `rootset` path selected the same priority-greedy set more slowly; both public names were removed in v0.x.
  - `sptrsv/` — triangular-solve backend (`omp.h` by default, `cuda.h` when `APXCHOL_USE_CUDA`; `critical_schedule.h` = the CPU critical-parent builder/weak barrier; `factor_drop.h` = the compacting drop shared by both; `transpose.h` = the CSC→CSR transpose shared by both (blocked counting-sort parallel path + serial scatter, `use_parallel_transpose()` rule); `cuda_host.h` = the CUDA-free host prep of the GPU backend — L11 extraction, drop, fp16 narrowing, transpose (via `transpose.h`), level schedules, dataflow batch tables; `cuda_levelset.h` / `cuda_dataflow.h` / `cuda_cast.h` = the device kernels' declarations, defined in `src/*.cu`). The GPU-resident PCG's own kernels are `solver/pcg_cuda_kernels.h` / `src/cuda_pcg_kernels.cu`. See "CPU SpTRSV schedules" below.

### Operator contract + M-matrix lumping (`include/apxchol/operator_class.h`, `src/operator_class.cpp`)

The class the solver is DEFINED on, asserted rather than guessed, in ONE place
every surface goes through — the CLI, the C++ API and both bindings:

    A = A^T,   a_ii > 0,   a_ij <= 0 for i != j.

`require_operator` throws `std::invalid_argument` naming WHICH condition failed
and with what counts: square → finite → symmetry → positive diagonal →
off-diagonal sign. Diagonal dominance is **reported, never enforced** —
`G3_circuit` (42% of rows) and `apache2` (2 rows) are legitimately non-dominant
and converge. A non-positive diagonal on a non-empty row is a hard PSD
violation (`e_i^T A e_i = a_ii`), and the ADJACENCY case is exactly that
condition failing everywhere while positive off-diagonals exist — so an
adjacency matrix is refused by the diagonal condition, with `apxchol.laplacian(A)`
/ `apxchol_laplacian(A)` / `--input-kind adjacency` named in the message. (This
replaced `detect_adjacency_signature`, a heuristic about the caller's INTENT
that could only recognise the one shape it had been taught.)

**M-matrix lumping** repairs a nearly-SDDM SPD operator instead of rejecting
it. For every positive off-diagonal pair, `a_ii += a_ij; a_jj += a_ij;
a_ij = a_ji = 0` — equivalently `Â = A + Σ a_ij (e_i - e_j)(e_i - e_j)^T`, a sum
of positive multiples of rank-1 PSD matrices, so `A ⪯ Â`: PSD in, PSD out; PD
in, PD out; row sums preserved exactly; dominance strengthened by `2·P_i`; all
edge weights `>= 0`, which is what `tree_elimination::sample_clique` needs (its
`prefix` array must be non-decreasing for the `upper_bound` draw — one negative
weight and the sampler draws from a broken distribution, and the bad fill
spreads by additive merging). Default **ON**: it cannot produce a wrong answer,
only a worse preconditioner.

What it buys tracks the positive off-diagonal MASS, not the entry count, and
the range is wide (measured 2026-08-20 against the same build with
`APXCHOL_LUMP=0`): `thermal2`, at 0.0017% of the mass, **survives without it**
— 46 iterations unrepaired vs 44 lumped — and `parabolic_fem` 44 vs 42; but
`bcsstk13` at 39.7% runs 500 iterations to a residual of **NaN** unrepaired,
and 50 to a stagnated 29.4 even lumped. Hence the ceiling.

It is applied ONLY to the matrix the PRECONDITIONER is built from, on a private
copy — PCG keeps applying the operator the caller passed, so the residual is
for the system asked about. Same contract as rchol's non-SDD compensation
(arXiv:2011.07769 §5.2.1). `operator_view` is the seam: it holds the lumped
copy when one is needed and is a plain reference to the caller's matrix
otherwise (a Laplacian/SDDM operator costs no copy). Every matrix-level
`factorize` goes through `detail::factorize_operator`, which is what keeps the
surfaces from diverging. The count lands on `factorization::lumped_offdiag`,
`solve_result::lumped_offdiag` and `Solver.lumped` (Python), and
`APXCHOL_VERBOSE` prints a one-line `describe_operator` summary.

Refused past `APXCHOL_LUMP_MAX` (default **0.25**) of the off-diagonal |mass|;
`APXCHOL_LUMP=0` disables lumping and lets the violation through with a stderr
warning (both arms of an A/B must produce a number). The ceiling is on MASS,
not entry count: `parabolic_fem` has 33% of its off-diagonals positive carrying
3e-6 of the mass. Measured basis in `operator_class.h`.

Measured as published (CLI, `--tol 1e-8`, T=8): `thermal2` 44 iters / 8.9e-09
(840 entries lumped, 0.0017% of mass), `parabolic_fem` 42 / 9.1e-09 (1048576
entries, 0.00016%), `apache2` 30 / 7.4e-09 and `G3_circuit` 45 / 8.6e-09 (both
have NO positive off-diagonals — lumping is a no-op there, they exercise the
non-dominant SDDM path), `bcsstk13` refused at 39.7% of the mass.

Cost is one O(nnz) parallel scan per factorize (binary-searching the transpose
partner inside `A` itself — no `A^T` materialized, no extra allocation).

### CLI input interpretation (`src/mtx_input.h`, target `apxchol_mtx_input`)

The CLI's HUMAN-FACING layer, one level above the contract. Nothing else
compiles it — the bindings deliberately do not, since a library caller does not
reliably see what we print. It may guess, because it prints its guess on every
run and takes `--input-kind` to override it.

A `.mtx` file may hold an assembled operator or a graph ADJACENCY/pattern
matrix (no diagonal, non-negative off-diagonals) — which is what most
SuiteSparse graphs and `scripts/download_graphs.sh` give you. The benchmark
suite never had the ambiguity: `load_mtx_as_adjacency` always reads `.mtx` as
adjacency.

`scan_input` → `resolve_input_kind` → `adjacency_to_laplacian` (Eigen-only, no
file I/O; unit-tested in `tests/test_mtx_input.cpp` plus eight `cli_*` ctest
cases over `tests/fixtures/*.mtx`). `--input-kind auto` (default) decides in
this order: no off-diagonals → operator; all off-diagonals non-positive →
operator; all positive → adjacency (a Laplacian/SDDM cannot have positive
off-diagonals); mixed signs with a positive diagonal on EVERY row → operator
(`parabolic_fem`, `thermal2`, `bcsstk*`); anything else → hard error naming the
counts. Explicit `laplacian` / `adjacency` override the READING and never fail
— but the library's contract assertion still applies afterwards, so forcing
`laplacian` on an adjacency file is refused there, not silently solved. Adjacency
assembly is `L = D - A`, `A_ij = |M_ij|`, self-loops dropped — the same reading
as `load_mtx_as_adjacency`, so it is a no-op on an already-assembled pure
Laplacian.

### Dispatch and customization seams

`apxchol::factorize` is templated on the IS selector (partitioner), the incidence storage, and — via overloads taking an instance — the eliminator. Custom eliminators/partitioners are passed as instances (matrix- or graph-level overloads; see `docs/extending.md` and `examples/`); partitioners implement one uniform `find_partition(G, span<const node_index> candidates, ctx, selection&)` shape — the `degree_prepass` trait decides whether the orchestrator runs the prune/degree/cap pre-pass (candidates = eligible list, vertex-indexed `ctx.degrees` filled) or passes the raw active list (`ctx.degrees` empty); selection knobs are grouped as `factor_options::partition`. The low-level `graph<>` and compile-time matrix overloads retain their indexed `vec_pool` type default; the high-level `solve`, `cpu_solver`, `apx_cholesky`, CLI, Python API and benchmark headline default to `vec_pool_aos`. The runtime-dispatch overload is:

The standard degree-prepass path keeps its exact ordering while parallelizing
the formerly serial setup scaffolding whenever `active.size() > omp_threshold`:
an exact byte-radix degree quantile (identical to `nth_element`), stable ordered
eligible filtering, and stable active-list compaction. `vec_pool` likewise builds
per-vertex grow metadata in parallel before one pool resize, and elimination
writes directly into the already-reserved final factor-column array instead of
moving a temporary vector-of-vectors after each round. These are unconditional

This dispatches storage from the `graph_storage` enum and the partitioner by name from `factor_options::is_select` (via `dispatch_partitioner` over `partitioner_list` in `partitioner_list.h`). ### Eigen integration

`apx_cholesky` (`include/apxchol/solver/preconditioner.h`) inherits `Eigen::SparseSolverBase` and is meant to be plugged into `Eigen::ConjugateGradient<SpMat, UpLo, apxchol::apx_cholesky>`. `analyzePattern` is a no-op; `factorize` calls into `apxchol::factorize` and then sets up the SpTRSV backend. Both `_solve_impl` (the Eigen entry) and `apply_fused` (the PCG-loop entry used by `cpu_solver`: takes Σr, returns r·z) share one body, `apply_core`.

### Determinism contract

What is reproducible, exactly. **The unit is (input, seed, thread count)** — everything below holds for two runs that agree on all three, and nothing below is claimed across different thread counts.

| | at T = 1 | at T > 1, same T | across different T |
|---|---|---|---|
| elimination order / `perm` | identical | identical | differs (the team size splits the candidate list, and that split is an input to the selection rule) |
| factor STRUCTURE — which `(row, col)` entries exist, `nnz(L)` | identical | identical | differs |
| factor VALUES | bit-identical | bit-identical on every workload measured (see the caveat) | differ |
| SpTRSV stored nnz after the compacting drop | identical | identical | differs with the factor |
| forward / transpose solve output, for one factor | bit-identical | bit-identical | **bit-identical too** — a solve is a pure gather (`tests/test_sptrsv_levelset.cpp`) |
| PCG reductions, iteration count, residual | bit-identical | bit-identical | differ at fp-rounding level |

Structure determinism at a fixed T > 1 rests on the partitioner contract in `solver/partitioner.h`: **a partitioner's output — the selected set AND the order it is added in — must be a pure function of (graph, candidates, ctx, team size).** The round's selection *is* the elimination order, which is the permutation, which is the factor's stored structure; a schedule-dependent selection therefore makes `nnz(L)` itself wobble run to run. The shipped block-greedy rule violated that contract until 2026-08-20 and is fixed at its site:

- **`block_greedy`** resolved cross-block conflicts by reading the shared `chosen[]` mask *while other threads were clearing it*, so a boundary pick dropped or survived depending on who got there first. Now the pass is decide-then-apply: every thread decides against the post-greedy snapshot, then a barrier, then the removals land. That always takes a chain's over-drop (a beats b beats c ⇒ both b and c go), which is exactly the worst case the racy pass already produced non-deterministically, so it cannot cost more IS than that pass already did on a bad interleaving: per-round IS sizes move ≤ 0.5% (120×120 grid, T=32, round 2: 1400–1405 racy across runs → 1398) and the round count stays inside the racy spread (44, vs 44–47). Solve quality does not get worse — PCG iterations at `--tol 1e-8` on grid 300×300 and 600×600 land at or below EVERY count the racy build produced over 3 runs each (300 at T=8: 43 vs 43/43/44, at T=32: 43 vs 43/45/46; 600 at T=8: 47 vs 47/48/49, at T=32: 46 vs 48/48/50). Symptom before the fix, on a 32-core box at the default `omp_threshold` = 2000, factorizing a 120×120 grid twice at one seed (`SpTRSVSetupMemory.SetupConsumingReleasesTheFactorAndSolvesIdentically`): **0/50 failures at T=1 and T=4, 19/50 at T=8, 16/50 at T=16, 19/50 at T=32**, with `nnz(L)` spreading over ~77250–77440. It passed under `ctest` only because `gtest_discover_tests` pins `OMP_NUM_THREADS=4`. This was **never** a regression — `block_greedy.h` is byte-identical from the initial public commit (`a6ca71b`) to `9e5d7b6` — it was invisible because the only determinism test, `FactorizeTest.Deterministic`, factorizes a 5×5 grid, i.e. 25 candidates against a 2000-vertex OpenMP gate, so it never executed the parallel branch at all.
  The deterministic conflict pass can over-drop and leave a non-maximal IS, so BG now repairs only the exact frontier a cross-block drop can have freed. The candidate-relative handoff rule removes the old small-tail motivation, but does **not** supersede the repair: on the two unstructured social cases where the frontier is large, current same-binary T=16 measurements make it a total-time win. com-Youtube (seed 42, three repair runs each bracketed by plain null arms) has median setup **5.40 -> 4.68 s** and total **13.00 -> 11.26 s**, even though iterations move 22 -> 23; as-Skitter with a component-consistent RHS has `nnz(L)` 18.439M -> 18.393M, iterations 27 -> 26, and paired process CPU time **-36%, -33%, -33%**. On grids/FEM its measured frontier work is 1.6-2.2% of the greedy+conflict scan. Rescue-only-at-bail and active-size floor/ceiling governors were built and rejected: they lose the early ordering effect or retain the extra rounds. The full frontier repair stays.
`priority_greedy` and `baumann_kyng` conform too (`priority_greedy` commits serially over candidate order; `baumann_kyng` selects from a hash sample). `priority_greedy` is the exact fixed-priority greedy MIS: parallel local-minimum passes are followed by an exact serial completion if their pass budget is exhausted. Its order comparison is lexicographic `(degree, full 64-bit hash, vertex)`, avoiding the old packed-key collision and degree overflow. Guard: `FactorizeDeterminism.*` plus `PriorityGreedy.SerialFallbackPreservesExactSelectedSetAndMaximality` in `tests/test_factorize.cpp`.

The naming/removal decision is measured, not cosmetic. The old `luby` implementation held priorities fixed within each elimination round, so it was priority-greedy rather than textbook Luby. Redrawing priorities per inner pass was checked in 90/90 bracketed records (10 matrices × 3 seeds × fixed/rerandomized/fixed, CPU T=16): one-RHS total geomean was 0.998×, with a repeatable YouTube win but a 1.062× grid_500 regression and mixed seed effects, so it did not replace the fixed rule. The Blelloch dependency-DAG `rootset` and the fixed-pass rule selected exactly the same set in 605/605 checked elimination rounds across six matrices; rootset's median setup ratio was 1.066× over the six-matrix timing sweep. `rootset` was therefore removed and the surviving rule renamed `priority_greedy` in v0.x.

**Caveat on VALUES at T > 1.** The elimination itself is written to be order-independent — per-vertex seeds (`run_seed ^ (v+1)·φ`), and `tree_elimination::sample_clique` sorts its neighbours by `(weight, vertex)` before sampling — so a fixed selection gives a fixed factor. What is not *proved* order-independent is the accumulation of several eliminated vertices' clique edges into the same graph edge within one round: that is an fp sum whose order follows the apply order. On everything measured here (4 storages × 4 partitioners × T up to 64, plus grid_500 at T=32) the values came out bit-identical, but treat "values may differ in the last ulps at T > 1" as the standing guarantee rather than "always bit-identical", and do not tighten a test to the stronger claim without measuring the workload it runs. `APXCHOL_TAIL_THREADS` (removed) deliberately broke this by applying clique edges in thread-arrival order.

**What is NOT deterministic anywhere:** the CUDA `cusparse` SpTRSV backend (`APXCHOL_GPU_SPTRSV=cusparse`; the AUTO dataflow backend *is* bit-deterministic — see the CUDA bullet above).

### PCG loop: fused, deterministic vector kernels

`cpu_solver::solve_impl` (`src/solve.cpp`) is not a chain of Eigen expressions: each iteration is four fused, OpenMP-parallel passes — `spmv+pAp` (p·Ap folded into the SpMV row loop), `update_xr_norm` (x += αp, r −= αAp, r·r, Σr in one pass), the preconditioner application (`pcg.solve.{permute,forward,back,unpermute+rz}`: input centering fused into the permute scatter, output re-centering + r·z fused into the unpermute gather — both centrings on centring applications only, see below), and `update_p`; after the loop, `center_x` (Laplacian only: x −= mean(x) once). Those are also the checkpoint labels under `pcg.*`. Every reduction uses the scheme in `preconditioner.h` `detail::` (fixed `static_chunk` partition, per-thread partials summed in thread order — never a `reduction()` clause), so results are bit-identical run to run for a fixed thread count (they differ across thread counts at fp-rounding level, like every other parallel pass). The passes engage their OpenMP team only above `APXCHOL_FUSED_PARALLEL_MIN` vertices (default 2000, `detail::fused_omp_min()`, read once): at or below it the SAME loops run on the encountering thread — bit-identical to a T=1 run. Do NOT raise the default to serialize mid-size problems: at n = 299k–335k (coAuthorsDBLP / com-Amazon) every gated pass measured FASTER parallel at T=16, and a serial stretch also starves the level-set SpTRSV around it (sleeping team) — 2026-08-19 calibration. `PcgFusion.*` in `tests/test_factorize.cpp` guards the parallel scheme (the test binary pins the threshold to its 2000 default); keep new vector passes on the same scheme.

### Laplacian vs SDDM rank

`factorization::sddm` distinguishes the two cases and changes the preconditioner application path:
- Laplacian (positive semidefinite, rank `n−1`): factor dimension is `n−1`; the application (`apply_core`) subtracts the mean of `b` before solving and re-centers the output afterwards — but only on every K-th application (the center-k schedule, K = 10 by default; see the env knobs below and `take_center_()`); the other applications skip both mean passes. `cpu_solver::solve_impl` restarts the schedule per solve (`reset_apply_count`) and subtracts `mean(x)` once from the returned solution (`center_x`), so the solution is min-norm regardless of K or of a warm start's constant.
- SDDM (positive definite, full rank): full `n×n` factor, no centering.

When touching `apply_core` or anything that constructs a `factorization`, check both branches.

### Experiment env knobs (`include/apxchol/env_knobs.h`)

Process-wide, read once. `APXCHOL_GROUND=center-k|reg` (+ `APXCHOL_CENTER_K`, `APXCHOL_REG_EPS`) selects how a pure Laplacian is grounded: `center-k` (the default, K = `APXCHOL_CENTER_K` = 10) centres only every K-th preconditioner application of a solve; K = 1 centres every application (`APXCHOL_GROUND=center` is accepted as an alias for K = 1, canonical spelling `center-k` + `APXCHOL_CENTER_K=1`); `reg` adds an explicit `eps·diag` self-loop at `make_graph` time so the matrix classifies as SDDM (full-rank factor, no centring). `APXCHOL_OMP_THRESHOLD` overrides `factor_options::omp_threshold` (unset = unchanged; it also gates the partitioners, so lowering it puts more rounds on the parallel selection branch and changes the factor — deterministically, since 2026-08-20. The earlier note here, that below-2000 values "make the factor structure nondeterministic via the racy `block_greedy` conflict resolution (12/50 failures at 256)", had the threshold wrong, not the race: the race fired at the DEFAULT 2000 too — it just needs enough threads for cross-block chains (0/50 at T=4, 19/50 at T=8 on a 120×120 grid). Both are fixed; see "Determinism contract"). `APXCHOL_LUMP=0` disables M-matrix lumping (default ON) so a nearly-SDDM operator is refused instead of repaired — the A/B knob; `APXCHOL_LUMP_MAX` (default 0.25) is the off-diagonal-|mass| ceiling above which lumping is refused. See "Operator contract + M-matrix lumping". The `APXCHOL_TAIL_THREADS` (parallel tail rounds) and `APXCHOL_FUSED_PARALLEL_MIN` (OpenMP engagement threshold of the fused vector passes) knobs were removed 2026-08-20 — see "Retired knobs"; `detail::fused_omp_min()` is now the constant 2000.

### CPU SpTRSV schedules (`include/apxchol/solver/sptrsv/omp.h`)

`APXCHOL_CPU_SPTRSV=auto|levels` is read at every CPU SpTRSV setup (unset = `auto`). `levels` is the established round-level kernel and the rollback. AUTO first builds those same levels, then, for a multi-thread setup with valid elimination-round metadata, replaces the maximal contiguous suffix of thin levels (at most `kSpTRSVOMPThreshold = 1024` rows each) with a critical-parent weak-barrier plan. This is a structural limiting rule rather than an input-size or matrix-name heuristic: no thin suffix is exactly level-set, and an all-thin factor is exactly the critical-parent plan. Both phases execute inside one persistent setup-sized OpenMP team; forward runs the fat prefix then the critical tail, while backward runs the critical tail then the fat suffix, with one phase barrier. There are no public `critical`/`hybrid` modes or tuning thresholds.

The critical-parent builder (`critical_schedule.h`) is an independent single pass over the selected factor rows, with no OSP/runtime dependency or search/refinement. Its factor scan is O(nnz+n); flattening the per-processor supersteps adds O(P*steps), with P bounded by the setup OpenMP team. A row follows a processor owning one of its latest parents, minimizing its earliest legal staleness-2 step; same-processor dependencies stay in topological row order and cross-processor dependencies are at least two steps old. Each solve uses monotone cache-line-separated per-processor counters and an architecture relax instruction after every failed poll (`pause` on x86, `yield` on AArch64). If OpenMP supplies fewer threads than setup requested (dynamic/nested/thread-limit), the parallel path touches no scheduled row and safely falls back to natural serial topological order. The flattened forward/back plans each store every tail row once; both schedules call the same row arithmetic.

The laptop validation used unrestricted boost, alternating arm order and paired medians. The fixed-factor campaign checked 45/45 primary jobs plus 20/20 thread-scaling jobs and a complete 13/20 supported-file holdout (the other seven inputs are nonsquare coordinate tables or violate the operator contract); all schedule outputs were byte-identical. Parent hybrid pair time was `0.654x` on the six primary targets, `0.619x` on the holdout, and improved monotonically from `0.961x` at T=2 to `0.641x` at T=16. The single-RHS campaign checked 31/31 cells and 279/279 records; after balancing the five marginal cells explicitly, AUTO total was `0.957x` on LiveJournal/T4, `0.938x` on LiveJournal/T8, `0.925x` on grid_500/T4, `0.991x` on iter0040/T2 and `0.965x` on shallow_water1/T16. The polling relaxation itself was isolated over 18 alternating LiveJournal/T8 pairs: median solve `0.753x`, total `0.887x`, with both order strata positive.

The strict Grace campaign (Daint job 4531713) checked 112/112 records and 28/28 cells: 14 matrices at T=16/72, `levels / old-spin / auto / levels`, with old/new arm order alternating. AUTO geomeans were setup `1.0145x`, PCG `0.5117x`, and single-RHS total `0.8091x`; total was `0.8495x` at T=16 and `0.7707x` at T=72, with all 28 cells positive. T16-to-T72 total scaling improved on all 14 matrices (relative speedup `1.011x` to `1.208x`). Every-poll AArch64 `yield` was neutral versus the old once-per-128 loop (`0.9998x` PCG, `0.9990x` total), so the x86 polling fix does not tax Grace. Every bracket preserved factor/stored nnz, iterations and printed residual; the remote and downloaded audits checked 448/448 result artifacts. The job consumed 53.04 allocated CPU-hours (11:03 on 288 CPUs).

`CriticalSchedule.*` validates every dependency, mixed/all-fat/all-thin limits, byte equality with level-set for fp32/fp16, in-place solves and runtime thread-count mismatch. `APXCHOL_LEVEL_DUMP=1` reports the level census and selected tail plan; `uses_hybrid_schedule()` exposes the resolved choice for tests and diagnostics.

Both schedules share ONE templated row kernel for both triangular directions and both storage types (`V = float | fp16_t`). Direction policies supply CSR-vs-CSC arrays, diagonal location and the fp16 back-input transform; `solve_row<Dir,V,Fat>` performs the same gathered dot and divide. In level-set mode, levels of at most `kSpTRSVOMPThreshold` (1024) rows run inside `omp single`, larger ones as `omp for schedule(static)`, one persistent team and one barrier per level. Level sets come from elimination rounds by default (`APXCHOL_ROUND_LEVELS=0` forces the topological scan and therefore keeps AUTO on level-set). A solve is a pure gather, so scheduling does not change arithmetic bytes. REMOVED negative variants remain removed: the old per-column sync-free back solve, nnz-balanced fat levels, and barrier-free thin-level agglomeration. They changed synchronization without preserving useful processor-local dependency chains and did not win across the suite.

### Compacting factor drop (`include/apxchol/solver/sptrsv/factor_drop.h`; both SpTRSV backends)

One implementation, `apxchol::compact_factor_columns` in `factor_drop.h` (templated on offset / index / value types), called by `omp_sptrsv::setup` on the factor's arrays and by `cuda_sptrsv::setup` (via `cuda_host::apply_factor_drop`) on its int32 host arrays before the upload — the two backends' compacted factors are identical (`GpuHostPrep.DropOnTheGpuHostArraysIsTheCpuDrop`); `kFactorDropRelDefault`, the env readers and `factor_column_scale` live there too (`omp_sptrsv::column_scale` / `factor_drop_rel_from_env` are thin wrappers). The description below is written for the CPU backend; on the GPU everything downstream of the drop (upload, cuSPARSE analysis, level-set transpose + schedules) sees only the compacted factor. `omp_sptrsv::setup` REMOVES factor off-diagonals below `rel * (column max |off-diagonal|)` before it builds its CSR/CSC (diagonal always kept; O(nnz) parallel, no atomics, deterministic; everything downstream — transpose, level sets — sees only the compacted factor) and folds each column's dropped mass back into its kept off-diagonals (column sums preserved — the factor of a Laplacian has zero column sums, which is what keeps `L L^T` a Laplacian and the grounded `L11 L11^T` a reduced Laplacian with the right grounding mass; plain removal turns every dropped tiny edge into extra grounding at both endpoints and cost iter0040 45 → 67 PCG iterations on the Laplacian path, see the header comment). **ON by default** at `kFactorDropRelDefault = 1e-4`; env `APXCHOL_FACTOR_DROP=<rel>` (read at every setup) overrides: `0` (or anything <= 0) disables it, any other value replaces the threshold; `APXCHOL_FACTOR_DROP_COMPENSATE=0` gives plain removal (A/B only). The default is measured, not guessed — see the comment on `kFactorDropRelDefault` (0 PCG iterations change on grid_500 / grid_2000 / iter0040 / com-Amazon; grids and social graphs drop nothing, iter0040 drops ~52% of its off-diagonals). `omp_sptrsv::drop_stats()` / `stored_nnz()` report nnz before/after; `APXCHOL_VERBOSE` prints a `[apxchol] sptrsv storage` line per setup and the benchmark's `APXCHOL_REPORT_FILL` FILL line prints `stored_nnz=`. Unit tests: `tests/test_sptrsv_drop.cpp` (every build) plus the storage-variant clause in `tests/test_lowprec.cpp`. When you need the un-dropped factor in the SpTRSV (an exactness argument, a byte-comparison against an external factor), run with `APXCHOL_FACTOR_DROP=0`.

### Setup memory lifetime (peak RSS)

Peak RSS is set during setup, not the solve, and it is an overlap of transients — keep the lifetimes below in mind when touching setup. `factorize_impl` frees the elimination state (working graph, per-thread `factorize_workspace` — T vertex-indexed dedup buckets — round scratch, `selection`) **before** `build_csc`; assembly reads only `factor_cols` (+ n), and this overlap used to be the process peak. `detail::factor_col::entries` is an exact-size range from one `std::pmr::monotonic_buffer_resource` per elimination thread, with values stored as `factor_value_t` (the factor's own precision — fp32, NOT the SpTRSV's storage type; narrowing there is bit-identical to narrowing at assembly). Resource ownership is moved out before the rest of `factorize_workspace` is released, so every range remains valid through CSC assembly; all ranges/resources are released immediately afterward. This avoids one independent heap allocation and geometric append-buffer growth per nonempty factor column. The capped Grace A/B checked 167/174 planned records (the seven missing records are late com-Orkut T=72 repeats), including 53/53 reachable PMR/main groups with identical factor nnz, stored nnz, iterations and levels; across 18 matrix/thread cells the setup/total/peak-RSS geomeans were 0.9930/0.9942/0.9783, with 5 setup wins beyond 1%, 13 cells within ±1%, and none worse beyond 1%. On the CPU path `apx_cholesky::install_factor` hands the factor to `omp_sptrsv::setup_consuming`, which calls `sparse_csc::release_values` on it the moment setup stops reading it (Laplacian path: right after its L11 copy) unless `set_keep_factor(true)`; `omp_sptrsv::setup(const&)` never releases; setup's own transients (L11 copy, compacted copy, transpose bucket, scratch) are released at their last use and `omp_sptrsv::memory_bytes()` is everything it keeps — `tests/test_sptrsv_memory.cpp` guards both (setup-only VmHWM vs the intended transient overlap; RSS after setup vs `memory_bytes()`). Freeing a `std::vector` means swap-with-empty — `v = {}` / `clear()` keep the capacity (same for `Eigen::SparseMatrix`: assign-from-empty keeps the buffers, use `.swap`). Verified peaks (T=16, `/usr/bin/time %M`, benchmark-style driver): iter0040 785 → 666 MiB, grid_2000 2337 → 2160 MiB, bit-identical factor/iterations at T=1.

### factor_options tuning knobs

`include/apxchol/solver/factor_options.h` is the authoritative source for tuning parameters. Several knobs have non-obvious empirical defaults documented in long comments there:
- `fs_compact_threshold = 0.0` (compaction off — empirically hurt grid and several IPM matrices when on).
- `min_is_fraction = 0.05` is a **candidate-yield base**, not an active-vertex fraction and not by itself a machine-granularity knob: the numerator is selected regions and the denominator is the vertices admitted by the current degree cap (20% quantile by default). Using all active vertices made 0.05 silently demand roughly 25% of the eligible pool; the historical `0.01` result was mostly the accidental correction `0.01 / 0.20 = 0.05`. A zero-sized result always bails. A non-empty result is protected while `active <= 2 * parallel_residual_threshold` (or twice the partitioner's default, 500 for BG/priority-greedy), because a bail near that boundary gives BK too little runway and turns almost the whole tail into singleton peel levels. A selection with at least `omp_threshold` vertices is also retained regardless of relative yield. On a large dense residual (`active > 4 * handoff` and `average_degree >= handoff`) the effective yield becomes `max(base, min(0.15, 3 * base))`; sparse and small residuals use the base exactly. `base = 0` disables yield-based handoff, including this adaptation; a smaller positive base postpones it and is the solve-quality / repeated-RHS setting. The 126-cell structural campaign behind the candidate-relative base covered 7 matrices × 3 seeds × plain/repaired BG × active-relative/candidate-relative/no-bail: candidate-relative was iteration-neutral throughout and removed the thermal2/G3/IPM tail cliffs.
  - **The dense-residual adaptation is a one/few-RHS setup trade, not a free solve win.** The audited GH200 campaign (`9446425` vs `3ffba25`, 183/183 records, CPU T=16/72 plus GPU smoke, 3 seeds where affordable) measured setup / PCG / one-solve-total ratios: as-Skitter `0.776/1.136/0.870` and `0.740/1.251/0.879`; com-LiveJournal `0.881/1.070/0.934` and `0.917/1.089/0.972`; com-Youtube `0.453/1.224/0.576` and `0.310/1.443/0.455`; kron_g500-logn16 `0.232/1.528/0.292` and `0.135/1.758/0.190`. Their measured setup-saving crossover is about 4.7/2.8, 4.3/2.0, 13.0/10.6 and 31.7/32.8 solves respectively; callers reusing one factor beyond that should lower the base. On the single measured Orkut seed the rule handed off much later than the rejected 0.10 rule (active ~195k, average degree ~951); T=16 total improved 3.5%, T=72 total regressed 1.2%, so do not generalize that cell without more seeds.
  - **Elimination teams are sized continuously from available work.** `process_vertex` is the indivisible unit: a singleton round is serial; a large independent set (`selected > omp_threshold`) uses at most one worker per pivot; a smaller round uses `min(selected pivots, available threads, floor(selected live-degree sum / 4096))`, with at least one worker. The live-degree sum is already produced by every selector prepass, including the BK residual loop, so this adds no graph traversal and uses neither an input-name/size heuristic nor an environment knob. Large independent sets retain `schedule(dynamic,64)`; smaller parallel rounds use one pivot per dynamic claim so a coarse chunk cannot hand the entire round to one worker. The rule replaces the former all-or-nothing `24 * omp_threshold` work gate: local Orkut tracing showed that 23,777 nominally serial rounds still carried 304.1M adjacency slots, 233.5M of them in small multi-pivot independent sets, while a full-team fork for each such round was also wasteful. Strict GH200 timing (job 4532834) checked 72/72 bracketed first-iteration records over nine matrices at T=16/72. Candidate-to-geometric-bracket geomeans were **0.9695 setup / 0.9468 eliminate / 0.9700 setup-plus-one-iteration total**; setup was `0.9696` at T=16 and `0.9694` at T=72. Orkut supplied the largest gain (`0.8766` / `0.8414` setup), and its relative T16-to-T72 setup scaling improved by 4.2%; as-Skitter regressed `1.0068` / `1.0106`, while coPapersDBLP reached `1.0180` at T=72. That timing run used `maxiter=1`; the separate full-convergence check (job 4532858) therefore ran one base/candidate pair for every cell through tolerance and checked **36/36 records, 18/18 cells**. Every pair had exactly equal factor nnz, stored nnz, iteration count and printed residual, and all 36 residuals were at most `1e-8`. Its unbracketed setup / PCG / full-single-RHS-total geomeans were `0.9666` / `0.9621` / `0.9650`; use these only as supporting timing evidence, not in place of the bracketed campaign. The legacy `merge_is` checkpoint covers the serial elimination path, not edge merging; moving rounds into work-sized teams therefore shifts time from `merge_is` to `compute+apply_fused`, and only the enclosing `eliminate` value is comparable. `APXCHOL_ROUND_TRACE=1` prints the selected-degree work plus the actual post-dedup neighbor and `d log d` work distribution across pivots, including the largest-pivot share and a deterministic LPT occupancy estimate. This diagnostic is the evidence gate for splitting one high-degree `process_vertex` across a team and does not run by default.
    Current-main scaling (Daint job 4538729, 189/189 timing records over the same nine matrices, three reps at T=1/2/4/8/16/36/72) reaches **5.387x setup / 9.649x partition / 3.224x elimination / 3.272x SpTRSV-setup** geomean speedup at T=72. Elimination is 41.9-60.0% of T=72 setup on every matrix, so it is the remaining setup-scaling limit. The accompanying 18/18 pivot traces reject a general intra-pivot fork: eight matrices keep parallel-round `d log d` LPT efficiency above 0.947 and put no more than 0.31% of total sort work in rounds below 80% efficiency; only Orkut is substantial (14.6%, worst LPT 0.576). Singleton-round sort work is large on kron (47.2%), Skitter (24.2%) and Amazon (22.0%), but their largest pivots are only 1310/1370/159 neighbors on the T=72 factors, too little work to fund a fresh 72-thread team. A persistent-team factorization would be a different mechanism; do not add a per-pivot fork under the current evidence.
  - **Candidate-induced region probe (diagnostic only).** `APXCHOL_REGION_PROBE=1` examines the degree-eligible candidate set at the first main-selector round, each subsequent active-size halving, and the selector handoff. It computes connected components of the induced residual graph on those candidates. Their complement is automatically a vertex separator, so the components are legal independent regions without a center/radius heuristic. The trace reports component counts, singleton count, largest region, internal/boundary edge work and deterministic LPT efficiency for the available team. It deliberately does not alter selection or elimination; use its output to decide whether restoring multi-vertex region elimination is justified. If components are all singletons the construction degenerates to an IS; if one component dominates, a production rule must split or fall back.
    Job 4538729 supplies that decision: early candidate-induced components are numerous and balanced on Skitter, LiveJournal, Amazon, G3 and kron (and Orkut has 452,757 components at round zero), but later snapshots usually collapse into one component carrying 75-100% of candidate work. The production prototype should therefore accept whole components only while they fit a deterministic work packing, and run the existing block-greedy rule inside/defer an oversized component. This is the desired structural interpolation: all singleton components are exactly an IS, balanced small components are independent regions, and one giant component falls back to the current selector. Do not restore the old k-ball/ND selectors or the old shared-pool multi-region mutation path merely because the component probe is positive; region-local elimination should keep intermediate fill private and defer only separator updates.
- `parallel_residual_threshold = SIZE_MAX` — this reads as "disabled" but is not: SIZE_MAX means *defer to the partitioner*, and `block_greedy` / `priority_greedy` both declare `residual_handoff_threshold = 500`, so the BK residual loop runs by default and the serial peel only ever sees the last ≤ 500 vertices. Under the adaptive candidate-yield rule, seed-42 repaired BG hands dense residuals to BK at about 9.1k active on as-Skitter, 74.8k on com-LiveJournal, 194.9k on com-Orkut, 4.35k on com-Youtube and 3.04k on kron_g500-logn16; coPapersDBLP remains on the 0.05 base and enters at 21.5k. IPM tails below the protected boundary and grids normally run to completion. Since 2026-08-20 the BK loop retries an empty round under the main loop's `kMaxEmptyRounds = 64` budget instead of bailing on the first one. The quantitative retry study below predates the candidate-relative denominator but isolates this BK-loop behavior: before the fix the handoff point was wherever the first hash-sample whiff happened to land (as-Skitter 5325 columns to the serial peel, coAuthorsDBLP 507). **The fix is fill-positive AND setup-positive.** Deterministic counters at T=16 (vec_pool, bg+tree, seed 42; identical across every rep in each arm): as-Skitter serial-peel columns 5325 → 500, BK rounds 2284 → 5236 productive + 864 whiffed, `nnz(L)` 19 430 230 → 18 479 113 (**−4.9%**), forward level count 7629 → 5756; com-LiveJournal 8216 → 500 peel columns, `nnz(L)` 122.54M → 120.62M (−1.6%); coAuthorsDBLP 507 → 500 peel columns, +110 nnz, 29 PCG iterations either way; com-Amazon never whiffs, so the retry alone leaves its factor bit-identical (the `est_avg_degree` seed below does change it). Paired same-binary A/B (arms by env, interleaved, 8 reps, T=16, medians) puts as-Skitter **setup at 0.98× of main** with `elim_remaining` 423 → 26 ms against `find_partition` 969 → 1171 ms and `eliminate` 903 → 1048 ms. An earlier session read this as "+4.2% setup"; that was noise — the honest noise floor on this box is the iter0040 control, which is **bit-identical across all arms** (it never enters the loop) and still swings 0.82–1.24× per rep and 0.94–1.03× on 5-rep medians. Treat anything under ±5% here as unresolved.
  - **BK's internal sampling constant is 0.1, with no public or environment knob.** Since sampled-adjacency work is approximately `active/c`, lowering `c` spends more work per round to expose a larger independent set and reduce residual rounds. A checksummed same-binary GH200 campaign checked 216/216 full solves and 54/54 exact baseline brackets over nine matrices, three seeds and T=16/72: against `c=0.3`, `c=0.1` gave setup / one-RHS-total geomeans `0.960/0.959` and `0.944/0.949`, factor nnz `0.998`, and iteration-delta sums −3 / 0. Every matrix-level total geomean was ≤1.002. `c=0.05` was faster (`0.948/0.930` total) but had the weaker quality margin (+3 iterations at T=72 and larger per-matrix seed excursions), so it is not the default. The x86 closure checked another 288/288 solves and 72/72 brackets at T=1/8/16, plus 96/96 solves and 24/24 brackets at T=2/4. `c=0.1` total geomeans were `1.010/0.994/0.972/0.998/1.014` at T=1/2/4/8/16; the T1 and small-control spread is below this laptop's measured noise floor, while the expensive parallel cells were substantial (Orkut `0.919/0.920`, LiveJournal `0.906/0.886`, coPapersDBLP `0.888/0.716` at T=8/16). A thread-scaled constant was rejected: `c=0.15` was slightly faster at T=2/4, but had a weaker iteration balance and would make factor structure depend on available threads for no demonstrated end-to-end gain. The research-only campaign override was never merged.
  - **Exact late-residual coalescing is ON under a conservative auto gate** for `vec_pool`; `APXCHOL_RESIDUAL_COALESCE=0` is the rollback. At a large BK handoff (`active >= 1024`), 256 evenly spaced active adjacency lists estimate the multiedge / distinct-pair ratio; only an estimate ≥ 4 rebuilds the active graph once. One physical edge stores the fp32-summed weight and a node-index multiplicity sidecar, so `prune_and_degree()` sees the old multigraph degree while numerical elimination sees the same aggregate it already formed transiently. This is not per-round hashing and not a dynamic pair map. Local Clang T=16 evidence: all five as-Skitter seeds clear the gate (estimate 4.96–6.18, exact 5.72–6.62), the seed-42 live graph heap at handoff is 720 → 49 MB, and three repeated residual-phase timings are 185–192 → 145–152 ms (rebuild/probe 40–47 ms, BK 158–166 → 91–93 ms, peel 26 → 13 ms); valid compatible-RHS iterations are 24/22/23/22/23 → 24/22/22/22/23. com-LiveJournal estimates 1.20 and is skipped (forcing its 1.20× rebuild regresses the residual phase 5.57 → 7.32 s); kron seed 42 estimates 3.91 and is skipped (the forced 3.34× rebuild sits at break-even and changes 14 → 15 iterations). coAuthorsDBLP and com-Amazon reach the ≤500 handoff without a probe. The rebuild can lower the later working set but briefly overlaps old graph + pending pairs + new graph; do not describe the 720 → 49 MB live-heap number as a proven peak-RSS reduction.
  - **Do not "fix" the tail by handing the peel more of the residual.** BK's yield does collapse on a dense residual (as-Skitter ~80 vertices/round at the handoff, ~0.4/round at active = 600 — a smooth power-law decay, no cliff), and a window-average "stop when the last 32 rounds averaged < y vertices" rule was built and measured against exactly that frontier. **Rejected: it buys no measurable setup and gives up fill.** as-Skitter at y = 1.0 stops at 2069 active, `nnz(L)` 18 479 113 → 18 648 027 (gives back 0.91 of the 4.90% win) for setup 0.973× vs 0.981× — inside the noise floor above. Forcing the handoff further out only makes it worse, monotonically: handoff at 500/1000/2000/3000/5325 gives `nnz(L)` 18.48/18.51/18.63/18.83/19.43 M and `elim_remaining` 26/65/172/285/423 ms against only 0/31/92/136 ms of `find_partition` saved. Same shape on com-LiveJournal (handoff 500/2000/5000/10000/20000 → nnz 120.6/120.7/121.3/123.4/128.8 M, `elim_remaining` 49/362/1326/4829/5302 ms) and on coAuthorsDBLP / com-Amazon, where setup is *lowest* at the 500 handoff. The reason is the elimination ORDER, not parallelism: residual rounds are almost never above `omp_threshold` (max IS over every residual round is 231 / 160 / 171 on as-Skitter / coAuthorsDBLP / com-Amazon; com-LiveJournal has 112 such rounds out of 13336), so a round runs the peel's own serial per-vertex code plus one BK scan — and it still wins because BK's degree-quantile cap picks a low-degree pivot: over the 4825 as-Skitter vertices between the two handoff points the rounds cost ~72 µs/vertex (202 ms `find_partition` + 145 ms `eliminate`) against ~82 µs/column (397 ms `elim_remaining`) for the same vertices in the `natural`-order peel. The whiffed rounds the rule was meant to stop paying for are nearly free: a whiff means the hash sample caught nothing, so there is no edge-visit work behind it — as-Skitter's 864 whiffs cost **2.5 ms total** (2.9 µs each), com-LiveJournal's 1583 cost 8.3 ms.
  - BK's round-0 degree seed is `2·m/|active|`, and `graph::m()` is **monotone** — it counts every edge ever added and is never decremented when elimination prunes one — so a BK instance started partway through an elimination reads a badly inflated average and under-samples its first round. The residual loop now pre-seeds `bk.est_avg_degree` from the main loop's last prepass average. Small and uniformly non-negative: BK rounds 735 → 732 / 463 → 455 / 5236 → 5252, `nnz(L)` −0.02% / −0.03% / −0.03% on coAuthorsDBLP / com-Amazon / as-Skitter, PCG iterations unchanged (29 / 36).
  - **The factor changes on any matrix that entered the loop, so the social-graph benchmark cells need re-baselining** (as-Skitter, coAuthorsDBLP, com-Amazon, com-LiveJournal, com-Orkut, com-Youtube …). Matrices that never enter it are bit-identical and need nothing: iter0040 and grid_2000 reproduce `nnz(L)` 9 055 788 / 21 872 680, 56 PCG iterations and their 16-digit residuals unchanged. Both changes are guarded by `BkResidualLoop.*` and `BaumannKyngSeeding.*` in `tests/test_factorize.cpp` (they fail 5/5 seeds and 1/1 respectively against the unfixed code).
- `residual_peel` defaults to `natural`; `min_degree` / `bk_serial` are opt-in for low-degree residuals.

If you change a default, re-read the rationale comment in `factor_options.h` before flipping it.

## Retired knobs

Every entry here was a real, measured experiment. It is recorded so nobody
re-adds the switch: the number is why the surviving behaviour is
unconditional. (Removed 2026-08-20 unless stated otherwise.)

| Knob | Was | Now | Measurement that retired it |
|---|---|---|---|
| `APXCHOL_SPTRSV_FP32` (CMake, ON) | fp32 vs fp64 SpTRSV factor storage | fp32, unconditional | never shipped, benchmarked or tested at OFF; the GPU dataflow kernel cannot do fp64 at all (its tagged word packs a 4-byte value next to a 4-byte epoch) |
| `APXCHOL_SPTRSV_LOWPREC` (CMake, `OFF`\|`FP16_SCALED`) | compile-time CPU fp16 storage | the runtime `APXCHOL_SPTRSV_FP16` | a storage width does not need a second binary; the CPU kernel is instantiated for both and branches once at setup |
| `APXCHOL_GPU_SPTRSV_FP16` | GPU-only fp16 switch | deprecated alias of `APXCHOL_SPTRSV_FP16` (stderr note) | one knob per axis; the two devices differ only in the unset default |
| `APXCHOL_GPU_SPTRSV=levelset` | the O(n)-schedule GPU backend | removed; the value lands on AUTO (dataflow) with a note | dataflow wins everywhere measured in one session: `gpu_pcg_loop` ms/iter iter0040 **0.98 vs 1.54**, grid_2000 **3.20 vs 6.26**; s/iteration com-Orkut **0.77 vs 0.87**, com-LiveJournal **0.21 vs 0.25** — at strictly less device state |
| `APXCHOL_FP16_DIAG=1` | divide by the fp16 diagonal slot instead of the fp32 `diag_[]` | fp32 `diag_[]`, always | iter0040 **44 → 50 PCG iterations (+14%)** (grid_500 40→40, grid_2000 47→47) — not neutral on IPM, so the 4 B/row `diag_` stays |
| `APXCHOL_FP16_KEEP_SUBNORMAL=1` | store fp16 subnormals instead of flushing | flush, always | iter0040 **64 iterations either way**: 1–10 significant bits at < 2^-14 of the column max are dead weight |
| `APXCHOL_LOWPREC_DIAG_COMP` | gate on folding the column's storage-rounding residual into the fp32 diagonal | applied, always, on CPU **and** GPU | without it the Laplacian path pays iter0040 **45 → 64 iterations**; with it fp16 matches fp32's counts. (It was already the GPU default and OFF on the CPU — the same variable with opposite defaults, which is exactly the kind of surface this pass removes.) |
| `APXCHOL_FP16_GATHER=simd\|scalar` | fat-level y-gather flavour of the fp16 kernel | the measured winner (`scalar`: vector widen into an 8-double stack buffer, scalar gathers, 4-way scalar FMA chain), always | the `_mm256_i32gather_pd` flavour loses **~10–15% solve on grid_2000 T=1** (equal on iter0040): vgatherdpd's latency sits on the critical path of the short grid rows |
| `APXCHOL_FACTOR_DROP_COMPENSATE=0` | plain removal instead of column-sum compensation | compensation, always (the `APXCHOL_FACTOR_DROP` threshold itself stays) | plain removal costs iter0040 **45 → 67 iterations** on the Laplacian path (48 → 48 on SDDM, where residuals stay orthogonal to the near-null direction) |
| `APXCHOL_TAIL_THREADS=<n>` | run a below-`omp_threshold` round's elimination on a pinned team of `n` instead of the serial tail | serial tail, always (`APXCHOL_OMP_THRESHOLD` stays) | tail 4 at threshold 2000 measured NEUTRAL-to-worse on iter0040 / grid_2000 (2026-08-19; 10-rep paired medians, setup 0.867 s serial-tail vs 0.869 s), and the parallel path applies clique edges in thread-arrival order, so it also costs the tail's bit-determinism |
| `APXCHOL_FUSED_PARALLEL_MIN=<n>` | vector length above which the fused PCG / preconditioner passes engage their OpenMP team | the constant 2000 the passes shipped with (`detail::fused_omp_min()`) | raising it is a LOSS at T=16 (2026-08-19, Zen 4, n ≈ 300k): `update_xr` 0.086 vs **0.396** ms/iter serialized, `permute` 0.089 vs 0.171, `unpermute+rz` 0.096 vs 0.236, `spmv+pAp` 0.62 vs **4.32**, and the sleeping team also starves the SpTRSV in between (forward 130 → 226 ms) |
| `APXCHOL_FTZ=1` | MXCSR FTZ + DAZ on the master and on every OpenMP team thread at PCG entry (sticky) | nothing — the bits are never set, and the code that set them is gone | **no subnormal ever enters this computation**, so the bits were a no-op costing one extra fork-join per solve. At T=1 (whole pipeline deterministic) FTZ on vs off gives a **byte-identical solution vector** on iter0040 (same md5, residual `8.074599861229295e-09` to all 16 digits, 57 iterations) and identical iterations/residual on grid_2000 (49, `7.813e-09`); the factor census agrees (`factor_subnormal` = **0** of 4.6M and 21.9M stored fp32 values). Zen 4 has no `assist` PMU event in this kernel's `perf list`; `ex_ret_ucode_ops` (the microcode path an FP denormal fixup takes on AMD) showed no FTZ signal above its own ±20% run-to-run spread |

## Source-of-truth caveats

- `benchmarks/src/v0/` holds the frozen v0 prototype sources (`simple_solver`, `graphs`, `mmio`) that the benchmark suite links as a baseline. The current library namespace is `apxchol::` under `include/apxchol/` — don't take API patterns from the v0 files.
- The `data/`, `results/`, and `benchmarks/results/` directories are gitignored, **except `results/cells/`** — the per-cell benchmark store is tracked (it is the source-of-truth the committed `benchmarks/latest/` charts are rendered from; ~1MB of JSON). Sweeps will produce cell diffs. `scripts/download_graphs.sh` fetches SuiteSparse matrices into `data/matrices/`.
- `cmake-build-*` directories are CLion artifacts; the canonical build dir is `build/`.
- **Benchmark cells are graded by one rule and one function.** `runner_common.classify()` marks a cell `complete` iff its harness-recomputed TRUE relative residual is `<= tol` exactly — every solver, ours included, no grace factor and no per-solver pass mark. A vendor's optimistic stop test is fixed at the vendor's knob (calibrate) or in `benchmarks/patches/` (patch), never by widening this comparison. Full statement and the per-solver ledger: [THE GRADING RULE](benchmarks/README.md#grading-rule) and [Whose solve loop produced each number](benchmarks/README.md#whose-solve-loop-produced-each-number).
