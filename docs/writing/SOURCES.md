# Sources and limits

Sources checked on 2026-11-03. This is a selected primary-source review, not a systematic literature review. Research reports, standards and practitioner guidance answer different questions. No cited study proves that this particular package improves agent output. Text here is original synthesis; linked works retain their own licenses.

## How recommendations are selected

This is an evidence-informed synthesis, not a claim that every recommendation is experimentally validated. Prefer directly relevant research, normative standards for the applicable scope, and established community or vendor guidance from the originating source. A famous source is insufficient if it addresses a different audience or task.

For each substantive recommendation, state the reader/task it helps, the supporting source, the source type, and any boundary or exception. Label additional thresholds and workflow choices as house guidance. Prefer a short rationale and example over a new prohibition. If sources disagree, explain the tradeoff or leave the choice to the project. Do not turn advice into a mandatory rule merely to make it mechanically testable.

Add guidance when it addresses a recurring consequential ambiguity or a distinct communication task. Keep general language principles in one place; use task-specific sections for differences. Keep operational authority, exact style budgets and project conventions local. Retire redundant or misleading guidance. Evaluate changes against factual preservation, reader understanding and task success; style-lint scores and instruction length alone are inadequate measures.

## Research

- **S18. John M. Carroll, Penny L. Smith-Kerker, James R. Ford and Sandra A. Mazur-Rimetz (1987), [The Minimal Manual](https://doi.org/10.1207/s15327051hci0302_2), Human–Computer Interaction 3(2), 123–153.** [Full paper](https://swcarpentry.github.io/swc-releases/2017.02/instructor-training/files/papers/carroll-minimal-manual-1987.pdf) reports two experiments on self-instruction for a word processor. Supports task-oriented learning, guided exploration and error recovery in that setting; does not establish that shorter is always better or that reference material should be omitted.
- **S19. Harald Weinreich, Hartmut Obendorf, Eelco Herder and Matthias Mayer (2008), [Not Quite the Average: An Empirical Study of Web Use](https://www.eelcoherder.com/images/publications/2008/not_quite_the_average.pdf), ACM Transactions on the Web 2(1), article 5, DOI 10.1145/1326561.1326566.** A 25-participant longitudinal browsing study documents rapid browsing and differences between users and site types. Supports designing for scanning, with important limits: observational behavior is not a universal reading percentage, causal proof of a word limit, or a measurement of today's interfaces.

- **S1. John Morkes and Jakob Nielsen (1997), [Concise, Scannable, and Objective: How to Write for the Web](https://www.nngroup.com/articles/concise-scannable-and-objective-how-to-write-for-the-web/).** Reports experiments comparing web-writing variants. Supports concise, scannable, objective presentation in that setting. Its measured gains are not transferable predictions for a CLI, scientific proof or agent-generated text. Does not establish our old numeric sentence/paragraph limits.
- **S2. Hoa Loranger and Kate Moran (2017), [Writing Digital Copy for Domain Experts](https://www.nngroup.com/articles/writing-domain-experts/).** Reports usability work with specialist readers. Supports scanability alongside factual depth and verifiability. A practitioner research report, not evidence that all experts want minimal detail.

## Documentation and language

- **S3. Daniele Procida, [Diátaxis](https://diataxis.fr/).** An established documentation framework separating tutorials, how-to guides, reference and explanation. Supports organizing by need; does not specify punctuation or mandatory page lengths.
- **S4. Google, [Developer documentation style highlights](https://developers.google.com/style/highlights).** Maintained technical-writing practice covering audience, tone, language and structure. A style guide, not an experimental result.
- **S5. Microsoft, [Writing tips for global communications](https://learn.microsoft.com/en-us/style-guide/global-communications/writing-tips).** Supports simple syntax, consistency and localization. Microsoft's [semicolon guidance](https://learn.microsoft.com/en-us/style-guide/punctuation/semicolons) prefers simplification but explicitly allows some uses. It does not support a universal punctuation ban.

## Errors and accessibility

The W3C links below are explanatory Understanding documents, which identify and link the normative success criteria. Applying a few writing rules does not establish full WCAG conformance.

- **S6. W3C, [WCAG 2.2 SC 3.3.3 Error Suggestion, AA](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html).** Known correction suggestions for detected input errors, unless security or purpose would be jeopardized. Scope is input assistance, not every possible runtime failure.
- **S7. GOV.UK Design System, [Error message](https://design-system.service.gov.uk/components/error-message/).** Government-service design practice for validation errors. Supports specific correction guidance; its stylistic conventions need context when used elsewhere.
- **S8. Tim Neusesser and Evan Sunwall (2023), [Error-Message Guidelines](https://www.nngroup.com/articles/error-message-guidelines/).** Practitioner guidance on visible, constructive errors that respect user effort. Does not require invented causes or every diagnostic code to be hidden.
- **S9. W3C, [SC 2.4.6 Headings and Labels, AA](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html).** Describe topic or purpose; no blanket ban on questions.
- **S10. W3C, [SC 2.4.4 Link Purpose (In Context), A](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html).** Context can establish a link's purpose. Standalone descriptive labels are a useful preference, stricter than the minimum criterion.

## Interface presentation

- **S11. Jakob Nielsen (2006), [Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/).** Established UX guidance for initially exposing important functions and deferring specialized ones. Its advice is not a mandate to hide all technical information or force a single fold everywhere.
- **S12. GOV.UK Design System, [Details](https://design-system.service.gov.uk/components/details/).** Avoid hiding information most users need. The [notification-banner guidance](https://design-system.service.gov.uk/components/notification-banner/) discourages excessive banners; this is a design-system convention, not a universal count constraint.
- **S13. IBM Carbon, [Empty states](https://www.carbondesignsystem.com/building-blocks/core/patterns/empty-states).** Distinguishes empty-state situations and constructive next steps. Does not justify banning every table cell that says “none”.
- **S14. W3C, [SC 4.1.3 Status Messages, AA](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).** Qualifying status changes must be programmatically determinable without taking focus; not every DOM update should be announced.
- **S15. W3C, [SC 1.4.10 Reflow, AA](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).** Includes exceptions for content requiring two-dimensional layout. Do not rewrite this as an unconditional ban on horizontal scrolling.
- **S16. W3C, [SC 1.4.12 Text Spacing, AA](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html).** Requires tolerating specified user spacing changes without loss of content/function. It does not mandate those values as the site's default styles.
- **S17. W3C, [SC 1.4.8 Visual Presentation, AAA](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html).** Covers adjustable text presentation, including line length. It is not an AA requirement or a requirement to use a particular CSS unit.

## Existing implementations

[Vale's package catalog](https://vale.sh/explorer) includes Google, Microsoft, write-good, proselint, RedHat and alex. Reuse selected upstream rules where their semantics match the project. Do not enable multiple complete styles blindly: their terminology and editorial conventions can conflict. The package's current YAML retains the earlier application's rule IDs for migration; that is compatibility work, not a claim to replace those guides.

This review recommends Google as the first technical-documentation style to trial, Microsoft for products already following its conventions, and selective proselint/write-good checks as suggestions. A whole-corpus comparison is still required before substituting those implementations. Semantic truth, task fit and rendered UI behavior remain outside regex linting.

## Engineering communication

- **S20. Google Engineering Practices, [Writing good CL descriptions](https://google.github.io/eng-practices/review/developer/cl-descriptions.html).** Supports specific summaries, motivation and a durable change record. Google's CL workflow differs from GitHub PRs; the guide here adapts the communication purpose rather than importing its entire process.
- **S21. Google Engineering Practices, [How to write code review comments](https://google.github.io/eng-practices/review/reviewer/comments.html).** Supports courteous, reasoned feedback on code and balancing specific advice with author discretion.
- **S22. Google Engineering Practices, [The standard of code review](https://google.github.io/eng-practices/review/reviewer/standard.html).** Prioritizes code health over perfection and distinguishes personal preference from substantive concerns. Does not override a consuming project's security or approval gates.
- **S23. Git, [SubmittingPatches](https://git-scm.com/docs/SubmittingPatches).** A project's contribution policy explaining self-contained motivation, imperative change descriptions and commit scope. Its trailer, wrapping and submission requirements apply to Git, not automatically to every consumer.
- **S24. Simon Tatham, [How to Report Bugs Effectively](https://www.chiark.greenend.org.uk/~sgtatham/bugs.html).** Established practitioner guidance on reproducibility and precise observations. Not a controlled study of a required issue template.
- **S25. [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/).** A widely used convention for curated release history. Its exact categories and versioning choices remain project decisions.
- **S26. GitHub, [Setting guidelines for repository contributors](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors).** Documents repository/organization contribution guidance and issue/PR templates. Supports discovering the receiving project's process; the specific pre-submission checks in this guide are our workflow synthesis.
- **S27. Alberto Bacchelli and Christian Bird (2013), [Expectations, Outcomes, and Challenges of Modern Code Review](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/ICSE202013-codereview.pdf), ICSE.** Observations, interviews, surveys and review-comment analysis at Microsoft identify understanding, knowledge transfer and alternative solutions alongside defect finding. This is empirical support for review's broader communication role, not a trial of our comment format or evidence that all organizations obtain the same benefits.

## Cognitive accessibility

- **S28. W3C Cognitive and Learning Disabilities Accessibility Task Force, [Making Content Usable for People with Cognitive and Learning Disabilities](https://www.w3.org/TR/coga-usable/) (2021).** Sections 4.3 and 4.4.9 cover organizing related content and separating instructions. Section 5.5.5 describes testing whether people can return to a task after distraction. This Working Group Note supplements WCAG. The example and review questions in P7 adapt that guidance. The Note does not establish a warning-line limit or demonstrate that this guide improves outcomes for people with ADHD.

## Teaching and explanation

Sources checked on 2026-11-08 for [TEACHING.md](TEACHING.md). DOIs were resolved through the Crossref API. Findings come from abstracts or full text. An entry says when it rests on search snippets or a secondary summary. Most learning-science studies tested school or university novices in short lessons. Applying them to self-paced articles for mixed readers is an inference.

### Learning science

- **S31. Sweller & Cooper (1985), [The Use of Worked Examples as a Substitute for Problem Solving in Learning Algebra](https://doi.org/10.1207/s1532690xci0201_3), Cognition and Instruction 2(1). DOI 10.1207/s1532690xci0201_3.** Research. Five experiments with Year 9, Year 11 and university students. Studying worked examples took less time than solving the same problems and led to faster, less error-prone solving of later similar problems (per abstract). Supports: show complete solved instances early. Limit: gains were specific to problems with the same structure as the examples. It does not show transfer to novel problem types.
- **S32. Atkinson, Derry, Renkl & Wortham (2000), [Learning from Examples: Instructional Principles from the Worked Examples Research](https://doi.org/10.3102/00346543070002181), Review of Educational Research 70(2). DOI 10.3102/00346543070002181.** Research (narrative review). Organises the worked-example literature into design principles. Integrate example components, label or segment to show conceptual structure, give several examples per problem type with varied surface features, place examples next to matched practice problems, and encourage self-explanation. Limit: the abstract ties examples to early skill stages. It is a narrative review, not a meta-analysis.
- **S33. Sweller, van Merriënboer & Paas (1998), [Cognitive Architecture and Instructional Design](https://doi.org/10.1023/A:1022193728205), Educational Psychology Review 10(3); and (2019), [... 20 Years Later](https://doi.org/10.1007/s10648-019-09465-5), EPR 31. DOIs 10.1023/A:1022193728205, 10.1007/s10648-019-09465-5.** Research (theory review). Cognitive load theory: novel information passes through a limited working memory, and stored schemas remove that limit. The 2019 paper summarises 20 years of follow-up work. Supports: cut extraneous processing for new material and build up schemas stepwise. Limit: it is a framework. Individual "effects" (redundancy, split attention and others) have their own evidence and boundary conditions. Load measurement is debated in the literature (not covered here).
- **S34. Kalyuga, Ayres, Chandler & Sweller (2003), [The Expertise Reversal Effect](https://doi.org/10.1207/S15326985EP3801_4), Educational Psychologist 38(1). DOI 10.1207/S15326985EP3801_4.** Research (review). Reviews studies showing that techniques that help inexperienced learners can lose their effect, or hurt, for experienced learners. Supports: decide who the reader is and avoid forcing experts through novice scaffolding (e.g. let them skip). Limit: "expertise" is relative to the specific material. The review does not give a reader-independent rule for how much detail to include.
- **S35. Renkl & Atkinson (2003), [Structuring the Transition From Example Study to Problem Solving in Cognitive Skill Acquisition](https://doi.org/10.1207/S15326985EP3801_3), Educational Psychologist 38(1). DOI 10.1207/S15326985EP3801_3.** Research (review + studies). Worked examples beat problem solving early, and problem solving is better later. Proposes "fading": successively remove solution steps from examples until learners solve alone. Reports supporting evidence (per abstract). Supports: progress from full examples to partial examples to exercises. Limit: making fading adapt to prior knowledge was posed as future work.
- **S36. Chi, Bassok, Lewis, Reimann & Glaser (1989), [Self-Explanations: How Students Study and Use Examples in Learning to Solve Problems](https://doi.org/10.1207/s15516709cog1302_1), Cognitive Science 13(2). DOI 10.1207/s15516709cog1302_1.** Research (think-aloud, correlational). Think-aloud protocols on worked mechanics examples. "Good" students generated many self-explanations that linked steps to principles and monitored their own understanding. "Poor" students did not. Supports: write examples so that each step's reason is recoverable, and prompt readers to explain. Limit: correlational, so the paper does not show causation.
- **S37. Chi, de Leeuw, Chiu & LaVancher (1994), [Eliciting Self-Explanations Improves Understanding](https://doi.org/10.1207/s15516709cog1803_3), Cognitive Science 18(3). DOI 10.1207/s15516709cog1803_3.** Research (experiment). Fourteen eighth-graders were prompted to self-explain each line of an expository text on the circulatory system. Ten controls read it twice. The prompted group gained more, and high explainers reached correct mental models (per abstract). Supports: embedded "why does this step hold?" prompts in expository text. Limit: very small sample, one topic and one age group.
- **S38. Roediger & Karpicke (2006), [Test-Enhanced Learning](https://doi.org/10.1111/j.1467-9280.2006.01693.x), Psychological Science 17(3). DOI 10.1111/j.1467-9280.2006.01693.x.** Research (experiments). Two experiments with students reading prose passages. Restudying won on a 5-minute test. Prior free-recall testing produced substantially better retention after 2 days and 1 week, even though restudy raised confidence (per abstract). Supports: end sections with exercises or recall questions. Limit: measures retention of prose, not problem-solving transfer. Readers of a web article may skip optional questions.
- **S39. Dunlosky, Rawson, Marsh, Nathan & Willingham (2013), [Improving Students' Learning With Effective Learning Techniques](https://doi.org/10.1177/1529100612453266), Psychological Science in the Public Interest 14(1). DOI 10.1177/1529100612453266.** Research (review). Rates 10 study techniques. Practice testing and distributed practice are high utility. Self-explanation, elaborative interrogation and interleaved practice are moderate. Rereading, highlighting, summarisation, keyword mnemonic and imagery are low. The tier ratings come from the monograph as reported in APS coverage and search summaries. The abstract lists the techniques. Limit: it rates learner strategies, not text design. Applying it to writing (e.g. including practice problems) is an inference.
- **S40. Fyfe, McNeil, Son & Goldstone (2014), [Concreteness Fading in Mathematics and Science Instruction: a Systematic Review](https://doi.org/10.1007/s10648-014-9249-3), EPR 26(1). DOI 10.1007/s10648-014-9249-3.** Research (systematic review). Recommends beginning with concrete materials and then explicitly and gradually fading to abstract representations. Concrete grounding helps interpret opaque symbols. Limit: this summary rests on search snippets because the abstract was not retrieved. The reviewed studies mostly concern school mathematics and science with physical or pictorial materials. They do not test prose algorithm articles.
- **S41. Guzzetti, Snyder, Glass & Gamas (1993), [Promoting Conceptual Change in Science: A Comparative Meta-Analysis...](https://doi.org/10.2307/747886), Reading Research Quarterly 28(2). DOI 10.2307/747886.** Research (meta-analysis). Later reviews quote its conclusion that text helps remove misconceptions when it is refutational or when combined with strategies that cause cognitive conflict. Limit: the abstract, pooled effects and sample were not retrieved, and the summary is secondary. Science misconceptions only.
- **S42. Tippett (2010), [Refutation Text in Science Education: A Review of Two Decades of Research](https://doi.org/10.1007/s10763-010-9203-x), Int. J. of Science and Mathematics Education 8. DOI 10.1007/s10763-010-9203-x.** Research (review). Two decades of studies favour refutation text over traditional expository text for conceptual change. The review found no developmental (age) relationship. This summary rests on search snippets of the abstract. Limit: science content. It does not establish which misconceptions are worth refuting.
- **S43. Schroeder & Kucera (2022), [Refutation Text Facilitates Learning: a Meta-Analysis of Between-Subjects Experiments](https://doi.org/10.1007/s10648-021-09656-z), EPR 34. DOI 10.1007/s10648-021-09656-z. Full text: [PMC8784251](https://pmc.ncbi.nlm.nih.gov/articles/PMC8784251/).** Research (meta-analysis). Random-effects meta-analysis of 44 independent comparisons (n = 3,869). Refutation text had a moderate positive effect, g = 0.41, versus other learning conditions, and the abstract calls it robust across contexts. Supports: state a common misconception, refute it, then explain the correct idea. Limit: comparison conditions are heterogeneous. Applying it to CS or algorithm misconceptions is an extrapolation.
- **S44. Mayer & Moreno (2003), [Nine Ways to Reduce Cognitive Load in Multimedia Learning](https://doi.org/10.1207/S15326985EP3801_6), Educational Psychologist 38(1). DOI 10.1207/S15326985EP3801_6.** Research (review of the authors' experiments). Builds on dual-channel, limited-capacity and active-processing assumptions. Proposes remedies for five overload scenarios. The remedies include weeding (removing interesting non-essential material), signalling (cues on how to process the material), segmenting with learner pacing, pretraining on component concepts, aligning words with the graphics they describe, and eliminating redundancy. The named remedies come from the abstract plus secondary summaries, and the full nine-item list was not re-read. Limit: mostly short narrated multimedia lessons with university students. Transfer to self-paced static text is partial: learners there already control pacing.
- **S45. Rey (2012), [A review of research and a meta-analysis of the seductive detail effect](https://doi.org/10.1016/j.edurev.2012.05.003), Educational Research Review 7(3). DOI 10.1016/j.edurev.2012.05.003.** Research (meta-analysis). Meta-analysis of the effect where interesting but irrelevant additions (anecdotes, decorative images) reduce learning. Effect sizes not quoted because the source was not accessible (publisher page 403). Limit: see S46 for moderators.
- **S46. Sundararajan & Adesope (2020), [Keep it Coherent: A Meta-Analysis of the Seductive Details Effect](https://doi.org/10.1007/s10648-020-09522-4), EPR 32. DOI 10.1007/s10648-020-09522-4.** Research (meta-analysis). University press coverage reports 58 studies with more than 7,500 students. Learners given seductive details scored lower. Reported moderators conflict across secondary summaries. Limit: no effect size quoted because it was not seen in the paper. The effect concerns irrelevant material. Relevant motivation and context are a different thing (see Diátaxis S58, Tao S54).
- **S47. Margulieux, Guzdial & Catrambone (2012), [Subgoal-labeled instructional material improves performance and transfer in learning to develop mobile applications](https://doi.org/10.1145/2361276.2361291), ICER '12. DOI 10.1145/2361276.2361291.** Research (experiment). Novices learning Android App Inventor from subgoal-labelled materials performed better on novel tasks (per abstract). Supports: label the purpose of each group of steps in a worked example. Limit: one block-based environment with novices.
- **S48. Morrison, Margulieux & Guzdial (2015), [Subgoals, Context, and Worked Examples in Learning Computing Problem Solving](https://doi.org/10.1145/2787622.2787733), ICER '15. DOI 10.1145/2787622.2787733.** Research (experiment). Compared giving subgoal labels with having learners generate them in an introductory programming task. Results were mixed and depended on other material features. Gains for the given-labels group did not replicate as expected (per abstract). Boundary: subgoal labelling is not a guaranteed win in CS.
- **S49. Sorva (2013), [Notional Machines and Introductory Programming Education](https://doi.org/10.1145/2483710.2483713), ACM TOCE 13(2). DOI 10.1145/2483710.2483713.** Research (literature review). Reviews misconception, mental-model and threshold-concept research. Argues that the "notional machine" (an abstract model of program execution) should be an explicit learning objective. Supports: show how state evolves (traces, invariants) and do not only show final code. Limit: argued recommendation for intro programming, not an intervention trial.
- **S50. Robillard (2009), [What Makes APIs Hard to Learn? Answers from Developers](https://doi.org/10.1109/MS.2009.193), IEEE Software 26(6); Robillard & DeLine (2011), [A field study of API learning obstacles](https://doi.org/10.1007/s10664-010-9150-8), Empirical Software Engineering 16(6). DOIs 10.1109/MS.2009.193, 10.1007/s10664-010-9150-8.** Research (survey + interviews). More than 440 Microsoft developers surveyed and interviewed. Many severe obstacles were tied to documentation. Five documentation factors emerged: intent, code examples, matching APIs to scenarios, penetrability and format. The details come from the abstract via search. Limit: one company, and API learning is task-oriented, so its relevance to explanatory articles is indirect. It does support including runnable, scenario-matched code.

### Mathematical and algorithms exposition

- **S51. Knuth, Larrabee & Roberts (1989), [Mathematical Writing](https://jmlr.csail.mit.edu/reviewing-papers/knuth_mathematical_writing.pdf), MAA Notes 14; Stanford report STAN-CS-88-1193.** Practice. Notes from Stanford CS 209 (1987), read in the PDF. §1 gives 27 rules. Examples: separate symbols in different formulas with words, and do not start a sentence with a symbol. Replace logic symbols with words in running text. State things twice in complementary ways, especially definitions. Sentences should still read smoothly when a reader skims the formulas. Never use the same notation for two things. Includes chapters on presenting algorithms and literate programming. Limit: expert craft advice, not tested on readers. The report-number and MAA attribution are bibliographic and did not appear in the PDF text extracted.
- **S52. Halmos (1970), [How to Write Mathematics](https://doi.org/10.5169/seals-43857), L'Enseignement Mathématique 16. DOI 10.5169/seals-43857 (ETH e-periodica).** Opinion (classic). Read in the ETH-digitised PDF. Sections include "Say something", "Speak to someone", "Organize first", "Write in spirals", "Honesty is the best policy", "Resist symbols" and "All communication is exposition". He advises organising around the central examples and counterexamples. Limit: one master's personal method, and the spiral plan is a drafting process rather than a reader-tested structure.
- **S53. Su (2015/2020), [Guidelines for Good Mathematical Writing](https://math.hmc.edu/su/wp-content/uploads/sites/10/2020/08/Guidelines-for-Good-Mathematical-Writing.pdf), MAA FOCUS Aug/Sep 2015 pp. 20-22 (handout updated 2020).** Practice. Read in the PDF. Lead rule: "Know your audience" (called the most important consideration). Also: set an invitational tone with "we", use complete sentences including around displayed equations, use paragraphs for related idea blocks, and choose good examples for difficult ideas. Shows a worked before/after solution. Limit: aimed at student proofs and solutions.
- **S54. Tao, [Advice on writing papers](https://terrytao.wordpress.com/advice-on-writing-papers/), incl. [Use good notation](https://terrytao.wordpress.com/advice-on-writing-papers/use-good-notation/), [Give appropriate amounts of detail](https://terrytao.wordpress.com/advice-on-writing-papers/give-appropriate-amounts-of-detail/), [Motivate the paper](https://terrytao.wordpress.com/advice-on-writing-papers/motivate-the-paper/), blog (undated, accessed 2026-11-08).** Opinion. Notation should stress the key parameters and suppress routine ones. Define global notation early and local notation near use, and follow conventions. Spend space on the novel and crucial parts and keep routine steps short. Still explain things that seem obvious only to the author. Tao: "Good notation can make the difference between a readable paper and an unreadable one." Limit: written for research papers read by experts. No dedicated "write for the reader" page exists, so cite the pages above.
- **S55. Gowers (2007), [My favourite pedagogical principle: examples first!](https://gowers.wordpress.com/2007/10/19/my-favourite-pedagogical-principle-examples-first/), blog.** Opinion. Argues that giving examples before a general definition makes the abstraction easier to grasp. He states explicitly that the approach should not be applied universally. Commenters note that examples can mislead (over-generalisation). Linked from Tao's advice page. Converges with concreteness fading (S40).
- **S56. Thurston (1994), [On proof and progress in mathematics](https://arxiv.org/abs/math/9404236), Bull. AMS 30(2):161-177. DOI 10.1090/S0273-0979-1994-00502-6.** Opinion (essay). Argues that mathematicians aim to advance human understanding, not only to produce formal proofs. Illustrates this with many distinct ways to think about the derivative (symbolic, geometric, as best linear approximation, and others). Read in the PDF. Supports: offer several complementary views of a key concept. Limit: reflective essay about research mathematics.
- **S57. Lamport (1995), [How to Write a Proof](https://lamport.azurewebsites.net/pubs/lamport-how-to-write.pdf), American Mathematical Monthly 102(7):600-608. DOI 10.1080/00029890.1995.12004627 (resolved via Crossref 2026-11-08).** Opinion (proposal + anecdote). Proposes hierarchically numbered structured proofs that make it much harder to prove false things. Read in the DEC SRC report version. He reports anecdotal evidence that perhaps a third of published papers contain mistakes. He also reports that checking readers like structured proofs while skimming readers are less happy, and suggests reading level by level. Limit: anecdotal, no controlled study. The format trades off skimmability.


### Explanation frameworks

- **S58. Procida, [Diátaxis: Explanation](https://diataxis.fr/explanation/) and [Tutorials](https://diataxis.fr/tutorials/), diataxis.fr (accessed 2026-11-08).** Practice. Explanation is understanding-oriented and discursive, and is read away from the task. It makes connections, gives context and reasons (design decisions, history, constraints), and admits alternatives and opinion. It should keep tight boundaries so instructions and reference move elsewhere. Tutorials are the opposite mode: learn by doing, with minimal explanation, a visible result at each step, no side paths, and reliability for every reader. Limit: a practitioner taxonomy, not empirically tested. An algorithm article mixes explanation with worked examples, so the split is a design choice.
- **S59. Google, [Technical Writing One: Audience](https://developers.google.com/tech-writing/one/audience), developers.google.com (accessed 2026-11-08).** Practice. Define the audience by role and proximity to the topic. List what readers need to learn minus what they already know. Beware the curse of knowledge (experts skip steps, use unexplained jargon). Use simple words and no idioms. Limit: course material, not a study.


### Motivated presentation of mathematics

- **S60. Pólya (1945), [How to Solve It](https://doi.org/10.1515/9781400828678), Princeton University Press. DOI 10.1515/9781400828678. Preface: [MacTutor reproduction](https://mathshistory.st-andrews.ac.uk/Extras/Polya_How_to_solve_it/).** Practice (classic). Organises problem solving into phases (understand, plan, carry out, look back) driven by heuristic questions, such as asking whether a related problem is known. The preface contrasts the Euclidean presentation (systematic, deductive) with mathematics "in the making", which looks experimental and inductive. Supports: show the questions that lead to a solution. Limit: heuristic advice drawn from teaching experience. It is not a tested account of how written text should be ordered.
- **S61. Pólya (1954), [Mathematics and Plausible Reasoning, Vol. 1: Induction and Analogy in Mathematics](https://doi.org/10.1515/9780691218304), Princeton University Press. DOI 10.1515/9780691218304. Preface: [cut-the-knot](https://www.cut-the-knot.org/books/plausible/preface.shtml).** Practice / opinion. Preface read. Finished mathematics looks purely demonstrative, but a theorem is usually guessed before it is proved, and students should learn guessing as well as proving. Pólya: "mathematics in the making resembles any other human knowledge in the making". Supports: show the conjecture and the evidence for it before the proof. Limit: he says plausible reasoning has no foolproof method and is learned by imitation, which leaves its classroom or text effect untested.
- **S62. Lakatos (1976), [Proofs and Refutations](https://doi.org/10.1017/CBO9781139171472), Cambridge University Press (eds. Worrall & Zahar). DOI 10.1017/CBO9781139171472. Appendix 2, ["The deductivist versus the heuristic approach"](https://www.cambridge.org/core/books/proofs-and-refutations/deductivist-versus-the-heuristic-approach/A31B134428AADB3464A6024FF93C5758).** Opinion (philosophy, historical case study). A classroom dialogue reconstructs the history of Euler's polyhedron formula as conjecture, proof, counterexample and repair. Appendix 2 (per the Cambridge summary) criticises the "deductivist style", which opens with axioms, lemmas and definitions that look artificial because the proof attempts that generated them are hidden. It recommends a heuristic style that shows the primitive conjecture, refutations and proof analysis. Supports: introduce a definition or hypothesis as the repair that a failed attempt forces. Limit: a philosophical argument from historical cases. Appendix text was seen only via the publisher summary and Wikipedia, not read in full.
- **S63. Leron (1983), [Structuring Mathematical Proofs](https://doi.org/10.1080/00029890.1983.11971184), Amer. Math. Monthly 90(3):174–185. DOI 10.1080/00029890.1983.11971184.** Opinion (proposal). Proposes presenting proofs in levels: main idea and the key construction first, with details and justifications in lower levels. Argues that linear proofs hide the intuition and make key steps look mysterious (per secondary summaries; the paper itself was not retrieved). Supports: state the plan and where the key object comes from before the details. Limit: one reported study of structured proofs found better summaries but slightly worse local comprehension. Its details could not be verified.
- **S64. Gowers, blog posts: [Discovering a formula for the cubic](https://gowers.wordpress.com/2007/09/15/discovering-a-formula-for-the-cubic/) (2007), the ["Demystifying proofs"](https://gowers.wordpress.com/category/demystifying-proofs/) category, and [Creating a database of motivated proofs](https://gowers.wordpress.com/2025/09/22/creating-a-database-of-motivated-proofs/) (2025); also [motivated proof examples](https://wtgowers.github.io/human-style-atp/motivatedproofexamples.html) (Human-style ATP project site).** Opinion / practice. The 2007 post shows how one might find the cubic formula "without just being told it", by trying natural guesses. It warns that a natural guess may fail and skips some routine computation. The 2025 post defines a structured motivated proof as one "generated by standard moves" (logic steps, known results, obvious examples, generalising or specialising), so no step is a rabbit out of a hat. The examples page contrasts the usual Cantor diagonal proof, where the set Y appears unexplained, with one that treats Y as an unknown and solves for it. Limits: Gowers says "obvious" is hard to define, routine proofs may not need motivation, and the project is an experiment aimed at AI training data, not a reader study. The phrase "how to discover proofs" was not found as a post title.
- **S65. Morris (2019/2020), [Motivated proofs: what they are, why they matter and how to write them](https://doi.org/10.1017/S1755020319000583), Review of Symbolic Logic 13(1):23–46. DOI 10.1017/S1755020319000583. [arXiv 2001.02657](https://arxiv.org/abs/2001.02657).** Opinion (philosophy of mathematical practice). Proposes that a proof is motivated if and only if readers can identify the task each step performs and where each step could reasonably have come from. Argues that such proofs promote understanding, convey reusable resources and stimulate discovery, and discusses how to produce them (per abstract). Limit: philosophical analysis with mathematicians' testimony. The author frames the definition as a proposal. No reader experiment. This is the closest formal statement of the principle.

### Reading and presenting proofs

- **S66. Lew, Weber & Mejía-Ramos (2020), [Do generic proofs improve proof comprehension?](https://doi.org/10.29275/jerm.2020.08.sp.1.229), J. of Educational Research in Mathematics 30(S):229–248. DOI 10.29275/jerm.2020.08.sp.1.229.** Research (interviews + randomised experiment). Generic proofs (a worked instance that shows the general argument) were popular with students, who expected them to help. In a randomised experiment students did not learn more from a generic proof than from a traditional proof (per abstract). Boundary: a natural, example-led presentation that readers prefer did not by itself improve measured comprehension.
- **S67. Roy, Inglis & Alcock (2017), [Multimedia resources designed to support learning from written proofs: an eye-movement study](https://doi.org/10.1007/s10649-017-9754-7), ESM 96(2):249–266. DOI 10.1007/s10649-017-9754-7.** Research (two experiments). e-Proofs added audio commentary and animations that pointed out logical relationships. Groups were similar at immediate test, but the e-Proof group retained less at a delayed test. Eye movements showed less processing effort when the audio was off. The authors suggest the extra support disrupted learners' own organisation of the material. Boundary: explaining every step for the reader can reduce the reader's own work and hurt retention.
- **S68. Hodds, Alcock & Inglis (2014), [Self-explanation training improves proof comprehension](https://doi.org/10.5951/jresematheduc.45.1.0062), JRME 45(1):62–101. DOI 10.5951/jresematheduc.45.1.0062.** Research (3 experiments). A short booklet that trains students to self-explain logical relationships in a proof significantly improved proof comprehension (per abstract). Overview of this programme: Alcock, Hodds, Roy & Inglis (2015), [Investigating and improving undergraduate proof comprehension](https://doi.org/10.1090/noti1263), Notices AMS 62(7), DOI 10.1090/noti1263 (DOI verified; text not read, the AMS host returned 403). Supports: prompt the reader to ask why each step holds (cf. S36, S37). Limit: trains the reader rather than changing the text.
- **S69. Lew, Fukawa-Connelly, Mejía-Ramos & Weber (2016), [Lectures in advanced mathematics: why students might not understand what the mathematics professor is trying to convey](https://doi.org/10.5951/jresematheduc.47.2.0162), JRME 47(2):162–198. DOI 10.5951/jresematheduc.47.2.0162.** Research (case study). A well-regarded professor's lecture was videoed. He described the ideas he meant to convey (including how to think about the proof). Six interviewed students did not grasp the ideas he considered central. Boundary: motivation the author intends may be invisible to readers unless stated explicitly. Limit: one lecture, six students, spoken rather than written.

### Exploring before or after instruction

- **S70. Mayer (2004), [Should there be a three-strikes rule against pure discovery learning?](https://doi.org/10.1037/0003-066X.59.1.14), American Psychologist 59(1):14–19. DOI 10.1037/0003-066X.59.1.14.** Research (narrative review). Reviews three decades of work (problem-solving rules, conservation, LOGO). In each, "guided discovery was more effective than pure discovery" for learning and transfer. Recommends cognitive activity with guidance and curricular focus. Supports: exploration should be guided toward a target. Limit: narrative review, no pooled effect.
- **S71. Alfieri, Brooks, Aldrich & Tenenbaum (2011), [Does discovery-based instruction enhance learning?](https://doi.org/10.1037/a0021017), J. of Educational Psychology 103(1):1–18. DOI 10.1037/a0021017.** Research (two meta-analyses, 164 studies). Explicit instruction beat unassisted discovery (d = −0.38 for discovery, 580 comparisons). Enhanced or assisted discovery (feedback, worked examples, scaffolding, elicited explanations) beat other forms of instruction (d = 0.30, 360 comparisons). Supports: guided exploration, never pure discovery. Limit: heterogeneous comparisons. Mostly live instruction, not expository text.
- **S72. Kirschner, Sweller & Clark (2006), [Why minimal guidance during instruction does not work](https://doi.org/10.1207/s15326985ep4102_1), Educational Psychologist 41(2):75–86. DOI 10.1207/s15326985ep4102_1.** Research (argument from cognitive architecture and studies). Minimally guided instruction is less effective and less efficient than strongly guided instruction for novices. The advantage of guidance recedes only when learners have enough prior knowledge to guide themselves (per abstract). The counterweight to the principle: an exploration that leaves the reader to search unaided is costly.
- **S73. Sinha & Kapur (2021), [When problem solving followed by instruction works: evidence for productive failure](https://doi.org/10.3102/00346543211019105), Review of Educational Research 91(5):761–798. DOI 10.3102/00346543211019105.** Research (meta-analysis, 53 studies, 166 comparisons). Problem solving before instruction (PS-I) beat instruction before problem solving (I-PS): g = 0.36 [0.20, 0.51]. With high fidelity to productive-failure design, g ranged from 0.37 to 0.58. Effects favoured I-PS for younger learners (grades 2–5) and for domain-general skills. A publication-bias adjusted estimate was g = 0.87, a model-based figure that should be treated cautiously. Limit: outcomes are mainly conceptual understanding and transfer. Most studies are live classroom activities, not reading.
- **S74. Schwartz & Martin (2004), [Inventing to prepare for future learning](https://doi.org/10.1207/s1532690xci2202_1), Cognition and Instruction 22(2):129–184, DOI 10.1207/s1532690xci2202_1; Schwartz, Chase, Oppezzo & Chin (2011), [Practicing versus inventing with contrasting cases](https://doi.org/10.1037/a0025140), J. of Educational Psychology 103(4):759–775, DOI 10.1037/a0025140.** Research (classroom experiments). 2004: invention activities before a lecture or reading gave better learning from a later resource than tell-and-practice. 2011 (N = 128 and 120): both groups used formulas equally well, but students who invented formulas from contrasting cases before being told learned the deep ratio structure better and transferred more often. Supports: let the reader see cases that pose the question before the formula. Limit: active invention by students. A text can only stage the contrast and ask.
- **S75. Ashman, Kalyuga & Sweller (2020), [Problem-solving or explicit instruction: which should go first when element interactivity is high?](https://doi.org/10.1007/s10648-019-09500-5), Educational Psychology Review 32(1):229–247. DOI 10.1007/s10648-019-09500-5.** Research (two experiments). Per search snippets (abstract not retrieved): for high element-interactivity material, explicit instruction followed by problem solving beat the reverse order on similar problems, with no difference on transfer in experiment 1. The authors conclude that instruction should come first when element interactivity is high. Direct disagreement with Kapur's productive-failure studies and S73. Limit: school students, two experiments. Sample sizes not confirmed in the primary text.

### Feedback

- **S76. Wisniewski, Zierer & Hattie (2020), [The Power of Feedback Revisited: A Meta-Analysis of Educational Feedback Research](https://doi.org/10.3389/fpsyg.2019.03087), Frontiers in Psychology 10:3087. DOI 10.3389/fpsyg.2019.03087.** Research (meta-analysis). 435 studies, more than 61,000 learners. Feedback had a medium average effect (d = 0.48) with substantial heterogeneity. The information content conveyed was a major moderator (per abstract). The full text describes Hattie and Timperley's task, process, self-regulation and self levels. It found the largest effects for high-information feedback, which covers task and process and sometimes self-regulation (full text read 2026-11-08). Limit: pooled effects across very different interventions do not predict the effect of a particular message.
- **S77. Van der Kleij, Feskens & Eggen (2015), [Effects of Feedback in a Computer-Based Learning Environment on Students' Learning Outcomes](https://doi.org/10.3102/0034654314564881), Review of Educational Research 85(4). DOI 10.3102/0034654314564881.** Research (meta-analysis). 40 studies, 70 effect sizes. Elaborated feedback such as an explanation (0.49) outperformed correctness-only feedback (0.05) and correct-answer feedback (0.32), particularly for higher-order outcomes. Effects were larger in mathematics than in the other subjects (per abstract). Limit: heterogeneous tasks. It does not fix a hint length or wording.
- **S78. Hattie & Timperley (2007), [The Power of Feedback](https://doi.org/10.3102/003465430298487), Review of Educational Research 77(1). DOI 10.3102/003465430298487.** Research (conceptual review). Feedback is among the major influences on learning, but its effect can be positive or negative depending on its type and delivery. Proposes a model of the properties and circumstances that make it effective (per abstract). Limit: conceptual model built on earlier meta-analyses.
- **S79. Kluger & DeNisi (1996), [Effects of feedback intervention on performance](https://doi.org/10.1037/0033-2909.119.2.254), Psychological Bulletin 119(2). DOI 10.1037/0033-2909.119.2.254.** Research (meta-analysis). 607 effect sizes. Feedback interventions improved performance on average (d = 0.41), but over a third decreased it. Effectiveness declined as feedback moved attention from the task toward the self (per abstract). Limit: mostly performance rather than learning outcomes, and moderators were "poorly understood".
- **S80. Shute (2008), [Focus on Formative Feedback](https://doi.org/10.3102/0034654307313795), Review of Educational Research 78(1). DOI 10.3102/0034654307313795.** Research (review). Formative feedback should be nonevaluative, supportive, timely and specific. Its success interacts with learner characteristics and the task. The review ends with guidelines (per abstract). Limit: narrative review. It does not support a ban on directive wording.

## Stewardship

Sources checked on 2026-11-08 for [STEWARDSHIP.md](STEWARDSHIP.md). Findings come from full text unless an entry says otherwise. The research measures the cost of configuration, technical debt and deprecation, and how often ideas fail. No source tests a stewardship review procedure. Applying these findings to a PR review is an inference.

### Stewardship research

- **S81. Tianyin Xu, Long Jin, Xuepeng Fan, Yuanyuan Zhou, Shankar Pasupathy and Rukma Talwadker (2015), [Hey, You Have Given Me Too Many Knobs! Understanding and Dealing with Over-Designed Configuration in System Software](https://doi.org/10.1145/2786805.2786852), ESEC/FSE 2015, 307–319. DOI 10.1145/2786805.2786852. [Authors' copy](https://cseweb.ucsd.edu/~tixu/papers/fse15.pdf).** Research (field study of user settings). Covers thousands of customers of a commercial storage system and hundreds of users of two open-source systems. Only 6.1% to 16.7% of parameters were set by most users, and up to 54.1% were rarely set by anyone. Up to 48.5% of configuration issues were difficulties finding or setting parameters. Their guidelines could hide or remove 51.9% of the commercial system's parameters with little impact on existing users. Limit: system software, not libraries or web APIs.
- **S82. Zuoning Yin, Xiao Ma, Jing Zheng, Yuanyuan Zhou, Lakshmi N. Bairavasundaram and Shankar Pasupathy (2011), [An Empirical Study on Configuration Errors in Commercial and Open Source Systems](https://doi.org/10.1145/2043556.2043572), SOSP 2011, 159–172. DOI 10.1145/2043556.2043572. [Authors' copy](https://www.sigops.org/s/conferences/sosp/2011/current/2011-Cascais/12-yin-online.pdf).** Research (546 real misconfigurations from a commercial storage system and four open-source systems). 70.0% to 85.5% were parameter mistakes. Many caused crashes, hangs or severe slowdowns. Supports counting misconfiguration risk as a cost of options. Does not measure how many options a system should have.
- **S83. Iago Abal, Claus Brabrand and Andrzej Wąsowski (2014), [42 Variability Bugs in the Linux Kernel: A Qualitative Analysis](https://doi.org/10.1145/2642937.2642990), ASE 2014, 421–432. DOI 10.1145/2642937.2642990.** Research (qualitative analysis of 42 bugs that appear only under some configurations). Abstract read. Shows that variability increases the complexity of bugs. Limit: one large C codebase, qualitative.
- **S84. Terese Besker, Antonio Martini and Jan Bosch (2019), [Software Developer Productivity Loss Due to Technical Debt: A Replication and Extension Study Examining Developers' Development Work](https://doi.org/10.1016/j.jss.2019.06.004), Journal of Systems and Software 156, 41–61. DOI 10.1016/j.jss.2019.06.004. [Authors' copy](https://research.chalmers.se/publication/511450/file/511450_Fulltext.pdf).** Research (longitudinal survey of 43 developers, 16 interviews, replication on an independent dataset). Developers reported losing on average 23% of their working time to technical debt. Extra testing was the most common added activity. Limit: self-reported time, and technical debt is broader than unneeded features.
- **S85. Meir M. Lehman (1980), [Programs, Life Cycles, and Laws of Software Evolution](https://doi.org/10.1109/PROC.1980.11805), Proceedings of the IEEE 68(9), 1060–1076. DOI 10.1109/PROC.1980.11805.** Research (laws inferred from observing large evolving systems). The second law says complexity increases as a program is changed unless work is done to maintain or reduce it. Limit: observational laws about a class of large systems, not a measured cost per feature.

### Practitioner reports

- **S86. Ron Kohavi and Stefan Thomke (2017), [The Surprising Power of Online Experiments](https://hbr.org/2017/09/the-surprising-power-of-online-experiments), Harvard Business Review 95(5), 74–82.** Practice (company experiment data reported in a practitioner magazine, not peer reviewed). At Google and Bing about 10% to 20% of experiments produced positive results. At Microsoft about one third proved effective, one third were neutral and one third were negative. Supports treating a proposer's confidence as weak evidence of value. Limit: consumer web products with A/B testing.
- **S87. Murali Krishna Ramanathan, Lazaro Clapp, Rajkishore Barik and Manu Sridharan (2020), [Piranha: Reducing Feature Flag Debt at Uber](https://doi.org/10.1145/3377813.3381350), ICSE-SEIP 2020. [Uber blog post](https://www.uber.com/blog/piranha/), 17 March 2020.** Practice (industrial experience report). Describes stale flags as technical debt that hurts reliability and maintenance. Reports cleanup changes for 1,381 flags, 17% of all flags, between December 2017 and May 2019. These figures come from the abstract as shown in search results and the conference listing. DOI 10.1145/3377813.3381350, resolved through Crossref.

### Standards

### Open-source proposal processes

- **S89. Rust, [RFC template](https://github.com/rust-lang/rfcs/blob/master/0000-template.md).** Practice. Motivation must explain the problem and give "several specific use cases". Drawbacks asks why the change should not be made. Rationale asks for alternatives and "What is the impact of not doing this?"

### API design and maintenance practice

- **S93. Joshua Bloch (2006), [How to Design a Good API and Why it Matters](https://www.cin.ufpe.br/~if669/files/MaterialDeEnsino/Referencias/api-design-oopsla-2006.pdf), invited talk, OOPSLA 2006 (slides).** Practice / opinion. "API should be as small as possible but no smaller." "When in doubt leave it out. You can always add, but you can never remove." Limit: experience-based guidance, not measured.
- **S94. Hyrum Wright, [Hyrum's Law](https://www.hyrumslaw.com/).** Practice (observation). With enough users of an API, all observable behaviors will be depended on by somebody, whatever the contract says. Supports planning removal before release.
- **S95. Martin Fowler (2015), [Yagni](https://martinfowler.com/bliki/Yagni.html).** Practice / opinion. Names the cost of build, delay, carry and repair for a presumptive feature. Says YAGNI does not apply to work that makes software easier to modify.
- **S96. Pete Hodgson (2017), [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html).** Practice. Treats toggles as inventory with a carrying cost and advises keeping it low. Describes removal tasks, expiry dates and caps on the number of toggles.
- **S97. Havoc Pennington (2002), [Free software UI](https://ometer.com/free-software-ui.html).** Opinion (desktop software maintainer). Argues that each preference has a cost: harder discovery, more testing, weaker defaults and less time for real features. Limit: desktop UI, essay.

### Product management and discovery

- **S103. Inge van de Weerd, Sjaak Brinkkemper, Richard Nieuwenhuis, Johan Versendaal and Lex Bijlsma (2006), [Towards a Reference Framework for Software Product Management](https://doi.org/10.1109/RE.2006.66), 14th IEEE International Requirements Engineering Conference (RE 2006). - **S99. 37signals, [Getting Real](https://basecamp.com/gettingreal), chapter ["Start With No"](https://basecamp.com/gettingreal/05.3-start-with-no).** Practice / opinion. - **S100. Clayton M. Christensen, Taddy Hall, Karen Dillon and David S. ### Compatibility, deprecation and usage

- **S104. Christopher Bogart, Christian Kästner, James Herbsleb and Ferdian Thung (2021), [When and How to Make Breaking Changes: Policies and Practices in 18 Open Source Software Ecosystems](https://doi.org/10.1145/3447245), ACM Transactions on Software Engineering and Methodology 30(4). DOI 10.1145/3447245.** Research (interview case study of Eclipse, npm and CRAN, then a survey, repository mining and document analysis across 18 ecosystems). Abstract read. Ecosystem norms on breaking changes shift the costs of using and maintaining software between stakeholders, according to each ecosystem's values. All ecosystems valued stability and compatibility.
- **S105. Anand Ashok Sawant, Romain Robbes and Alberto Bacchelli (2018), [On the Reaction to Deprecation of Clients of 4 + 1 Popular Java APIs and the JDK](https://doi.org/10.1007/s10664-017-9554-9), Empirical Software Engineering 23, 2158–2197. DOI 10.1007/s10664-017-9554-9. [Authors' copy](https://anandsaw.github.io/publications/emse2017.pdf).** Research (repository mining of more than 25,000 GitHub clients of five Java APIs and 60 JDK clients). Only a small fraction of clients reacted to deprecation. Very few replaced the deprecated call. Limit: Java, and deprecation policies differ between APIs.
- **S106. Aline Brito, Laerte Xavier, André Hora and Marco Tulio Valente (2018), [Why and How Java Developers Break APIs](https://doi.org/10.1109/SANER.2018.8330214), SANER 2018, 255–265. DOI 10.1109/SANER.2018.8330214. [arXiv 1801.05198](https://arxiv.org/abs/1801.05198).** Research (field study, 59 breaking changes confirmed by developers of 19 projects). Abstract read. Breaking changes were mostly motivated by new features, by making APIs simpler with fewer elements, and by maintainability. Limit: small sample of Java libraries.
- **S107. [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).** Standard (community specification). Deprecating public API functionality needs a minor release, and the deprecation must appear in at least one minor release before removal in a major release. Applies to projects that adopt SemVer.
- **S108. Go, [Go 1 and the Future of Go Programs](https://go.dev/doc/go1compat).** Practice (a project's compatibility promise). Programs written to the Go 1 specification should keep compiling and running. Lists exceptions such as security fixes, unspecified behavior and bug fixes. Shows one project's explicit compatibility contract, not a general rule.
- **S109. Hyrum Wright, "Deprecation", chapter 15 of Titus Winters, Tom Manshreck and Hyrum Wright (eds.) (2020), [Software Engineering at Google](https://abseil.io/resources/swe-book/html/ch15.html), O'Reilly.** Practice. States that code is a liability, not an asset. Advisory deprecation with warnings and no deadline rarely moves existing users. Compulsory deprecation with a deadline and a dedicated owner works better. Advises planning for retirement when a system is built. Limit: a large company with a monorepo.
- **S110. Russ Cox (2023), [Transparent Telemetry for Open-Source Projects](https://research.swtch.com/telemetry-intro), research!rsc, 8 February 2023.** Practice / proposal. Argues that bug reports and surveys miss how open-source software is used, and proposes minimal, public usage counters. The post notes that the design became opt-in. Limit: one project's design proposal.

### Evidence not carried forward

- **S102. Mountain Goat Software (Mike Cohn's site, last updated 2016), [Are 64% of Features Really Rarely or Never Used?](https://www.mountaingoatsoftware.com/blog/are-64-of-features-really-rarely-or-never-used).** Practice (critique). The widely repeated claim that 64% of features are rarely or never used comes from a Standish Group talk at XP 2002. The post reports that it was based on four internal applications at four companies, none of them commercial products. We did not find the original data and do not use the figure.
